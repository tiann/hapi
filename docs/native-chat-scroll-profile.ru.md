# Прокрутка нативного чата: измерения на симуляторе

Дата: 2026-09-10. Базовая линия бизнес-кода: `5194271f`.

## Выводы

1. **Приоритет — оптимизировать в iOS разностное обновление и измерение сложного контента, а не продолжать слепо оптимизировать индекс списка.**
   Обычный текст близок к 60 Гц; сложный Markdown стабильно даёт интервал обратного вызова кадров около 33 мс.
   Наложение обновлений сообщений ухудшает ещё сильнее. Однопеременные эксперименты подтвердили дополнительную стоимость «обновления неизменившихся видимых строк».
2. **Android обязан различать работу приложения и шум симулятора.** Большинство прогонов близки к 60 Гц,
   но полный повторный прогон давал и 47–52 FPS, и длинные кадры свыше 600 мс; нельзя показывать только удачные прогоны.
   В цепочке вызова длинного кадра есть `postAndWait` ожидания главным потоком RenderThread, что не следует напрямую приписывать
   перекомпоновке списка Compose. Сохраните исходные аномальные данные и добавьте контролируемые эксперименты с офлайном и записью планирования.
3. **Диагностическая упрощающая оптимизация в прогоне локализации была откатана.** Позже была реализована разностная
   перерисовка с сохранением hosting roots и мостом к живому renderer/environment; см. ниже «Реализация оптимизации iOS». Высоты строк не замораживались и
   передача темы, шрифта, содержимого и окружения взаимодействия не прекращалась ради бенчмарка.

## Границы измерения

- Хост: Apple M4 Pro, 14 ядер, 48 GiB; macOS 26.6.2, Xcode 26.6.
- iOS: выделенный iPhone 15 / iOS 26.5 Simulator, Release `-O` / whole-module
  optimization, `ENABLE_TESTABILITY=YES`, запрос обратного вызова отображения 60 Гц.
- Android: выделенный API 35 ARM64 эмулятор, 1080 × 1920 / 420 dpi, 4 vCPU / 4 GiB;
  `-gpu host`, логи подтверждают Apple M4 Pro / Metal, а не SwiftShader из старого скрипта.
  Сборка `profile`: не debuggable, без обфускации, отладочная подпись; не APK для магазина.
- Обе платформы запускались последовательно, не одновременно под нагрузкой. 800 синтетических сообщений с реальными рендерерами строк чата,
  кешем Markdown и нативными списками, а не геометрическими заглушками; каждый сценарий повторялся 3 раза.
- Обычный текст; сложный Markdown (заголовки, списки, 14 строк кода, таблица 10 строк × 3 столбца, цитата);
  сложный Markdown + 10 обновлений хвостового сообщения вне экрана в секунду. AST прогревались до начала.
- iOS: реальный CADisplayLink, непрерывная прокрутка 1 800 pt/s по 6 секунд за прогон.
  Android: реальное перетаскивание MotionEvent и естественное замедление, 8 раз за прогон; **без виртуальных часов тестов Compose**.
- Не включает время Hub/сети/сведения сообщений; не покрывает приход страниц, декодирование изображений, клавиатуру, 120 Гц,
  очень длинный код, реальные пользовательские сессии или устройства нижнего сегмента. Числа нельзя сравнивать между платформами напрямую, и они не означают приёмку релиза.

### Что именно означает «FPS»

- Instruments `Animation Hitches` в iOS явно возвращает **«Hitches is not supported
  on this platform»**. Поэтому ниже — **фактическая частота обратного вызова CADisplayLink**, а не итоговые
  представленные FPS композитора. P95/P99 — по интервалам обратного вызова по стенным часам; `>25 мс` — диагностический порог, а не метрика hitch Apple.
- Time Profiler attach в этом окружении не отвечал и был завершён; доказательства CPU взяты из отдельного
  сэмплирования стека вызовов macOS `sample` с интервалом 1 мс. Прогоны с накладными расходами сэмплирования не используются для базовой линии частоты кадров.
- Android записывает одновременно обратные вызовы Choreographer, Window.FrameMetrics, gfxinfo и
  Perfetto FrameTimeline. Частота представления считается только по интервалам непрерывного представления **внутри интервала перетаскивания HapiGesture**;
  нельзя делить общую длительность теста (со паузами) на число кадров.
- У FrameTimeline на этом эмуляторе много `Prediction Error` / `Early Present`,
  поэтому нельзя считать все `jank_type != None` пропусками кадров приложением. Пропуски дедлайна приложением сообщаются отдельно.
  Поля приходят из разных временных границ, и число превышений бюджета FrameMetrics не равно числу missed FrameTimeline.

Диагностический эксперимент удалял только `|| visibleIDs.contains($0.id)`, остальной код и вход не менялись, процесс перезапускался,
три прогона повторялись, затем исходный файл восстанавливался:

| --- | ---: | ---: |
| Обычный текст | 59,84 → 59,84 /с | 3 → 3 |
| Сложный Markdown | 56,22 → 56,11 /с | 68 → 70 |

и статический сложный список тоже не улучшился. **Нельзя просто выпускать это удаление строки**: тема, Dynamic Type,
locale, basePath, изменения окружения ссылок/взаимодействия всё равно должны доходить до существующих hosting cells.

## Реализация оптимизации iOS: сохранение hosting roots

Изменения ограничены списком и входом чата, без переписывания Markdown/протокола:

- `reconfigureItems` обрабатывает только изменения содержимого или ширины и больше не добавляет безусловно все видимые ID.
- Каждый hosting root сохраняет лёгкую обёртку SwiftUI, читающую общий observable renderer.
  Последний builder, basePath и прочие захваты обычных значений и action captures продолжают передаваться; SwiftUI сам
  сравнивает возвращаемое представление, вместо того чтобы UIKit каждый раз переустанавливал hosting-конфигурацию.
- В `updateUIViewController` читается `context.environment` и единообразно мостится в существующие и новые строки.
  Перечисление сравнимых ключей окружения не делается; тема, Dynamic Type, locale, направление и пользовательские сервисы сохраняются.
  В экспериментах выяснилось: чтение `@Environment(\.self)` родительского представления только в «убегающем» builder может пропускать
  зависимости обновления окружения. Поэтому ручной снимок на входе чата убран, а распространение возложено на список.
- Сериализация снимков, компенсация анкеров, асинхронный self-sizing, подтверждение раскладки скрытых страниц и защита от дублирующихся ID не меняются.
  **Лёгкая обёртка всё ещё обновляется; это не заявление о нулевой работе SwiftUI и не пропуск всех измерений.**

Новое регрессионное покрытие: бюджет нулевой переконфигурации видимых cell при обновлении вне экрана, рост видимой строки и анкер, последнее
содержимое после переиспользования, обновления темы/basePath/действий ссылок для того же Item, изменения языка/направления/размера шрифта и повторное измерение.
UIKit сам может запрашивать cell при изменении трейта направления; это не относится к безусловному обновлению сообщений.

Повторные измерения используют те же Release-сценарии в порядке «новая реализация → повторный прогон старой → повторный прогон новой», каждый в отдельном
процессе и на выделенном симуляторе. В этом прогоне добавлены скриншоты рендера перед замером и утверждения высоты видимых сложных строк; скриншоты просмотрены локально;
начальные высоты строк у старой/новой реализации совпадают. Скриншоты вне интервала замера, но могут влиять на прогрев, поэтому
**выгода сравнивается только с повторным прогоном старой реализации на том же тестере этого прогона, а не вычисляется напрямую из 54,29 /с предыдущего прогона.**

| Сценарий | Повтор старой, среднее | Новая, 1-я / 2-я партия, среднее | >25 мс: старая / новая 1-я / новая 2-я |
| --- | ---: | ---: | ---: |
| Обычный текст | 59,83 /с | 59,84 / 59,84 /с | 3/1 078 / 3/1 079 / 3/1 080 |
| Сложный Markdown | 59,73 /с | 59,34 / 59,45 /с | 5/1 078 / 12/1 070 / 10/1 073 |
| Сложный Markdown + обновления | 57,89 /с | 59,12 / 59,06 /с | 38/1 044 / 16/1 066 / 17/1 064 |

По три прогона каждого сценария в каждой партии. Объединённые две партии новой реализации: среднее в сценарии обновлений 59,09 /с, примерно +2,1 % к старой реализации этого прогона,
доля длинных интервалов 3,64 % → 1,55 %. Статические сложные сценарии не улучшились и немного просели; у старой реализации в сценарии обновлений
тоже были различия прогонов 58,84, 58,84, 56,00 /с.
Поэтому основной детерминированный выигрыш — **устранение лишней переконфигурации cell**, и на его основании нельзя обещать полные кадры на реальном устройстве.
В этом прогоне не добавляется кеш высот сложных строк и не меняется вёрстка блоков кода/таблиц; корректность динамических измерений сохраняется, а дальнейшая оптимизация сложных строк
будет решаться по стеку вызовов длинных кадров на реальном устройстве.

Финальная проверка: Debug **14 проверок пройдено** (включая утверждения объёма работы); Release по **13 проверок пройдено** в каждой партии
(включая opt-in тесты кадров). В Debug одна проверка заняла около 650 секунд из-за сна хоста: `pmset` подтверждает сон системы с 13:16 до 13:27, это не данные длинного кадра приложения;
соответствующая регрессия в Release — около 0,33 секунды.
Все сценарии замера длятся около 6 секунд на прогон; длительность обычных тестов не используется как доказательство производительности кадров.

Исходные записи: `/tmp/hapi-scroll-live-environment*`, `/tmp/hapi-scroll-baseline-control*`;
превью рендера и JSON по прогонам остались в соответствующих attachments xcresult, проверены только локально и не загружались.

## Android: полные результаты, а не лучшие прогоны

При первом запуске в большинстве прогретых прогонов FrameMetrics P95 составлял 4–7 мс, Choreographer около 59,9 /с;
в первом прогоне обычного текста P95 21,20 мс. В этом прогоне кольцевой буфер trace на 64 MiB сохранил только последние пять сценариев;
JSON/gfxinfo приложения полны для девяти прогонов, но этот trace не считается полным доказательством девяти прогонов.

Расширение до 256 MiB и повторное измерение с реальными маркерами перетаскивания:

| Сценарий / прогон | Частота представления в интервале перетаскивания | P95 интервала представления | Пропуски дедлайна приложением |
| --- | ---: | ---: | ---: |
| Обычный текст 1 / 2 / 3 | 59,39 / 59,95 / 60,12 FPS | 24,90 / 19,21 / 18,10 мс | 3 / 0 / 0 |
| Сложный контент 1 / 2 / 3 | 51,66 / 49,55 / 60,13 FPS | 19,02 / 40,23 / 19,45 мс | 1 / 37 / 1 |
| Сложный контент + обновления 1 / 2 / 3 | 59,78 / 59,60 / 47,58 FPS | 19,41 / 18,38 / 21,21 мс | 0 / 0 / 4 |

Дрожание границ короткого окна сэмплирования/меток времени может дать оценку чуть выше 60, это не значит, что устройство превысило частоту обновления.
В последнем прогоне сценария обновлений максимум FrameMetrics составил 688,15 мс — это нельзя скрывать одним средним FPS.
В trace есть `draw-VRI → postAndWait` около 609 / 625 мс: главный поток ждёт поток рендеринга;
есть и длинные сегменты перекомпоновки. По trace только с view/gfx нельзя определить, работают ли эти сегменты или вытеснены.
Фоновая работа GMS/Play Store на новом эмуляторе в тот же период всё ещё активна; это лишь намёк на конкуренцию окружения, а не окончательный вывод.

Контрольный эксперимент: на выделенном эмуляторе включён режим полёта, отключено самообновление Play Store, ожидание 30 секунд;
добавлены `sched_switch` / `sched_waking` и метаданные процесса. Собрано 495 548 сегментов планирования,
все девять тестовых сегментов полны; результаты **без изменения бизнес-кода приложения**:

| Сценарий | Частота представления в интервале перетаскивания, диапазон трёх прогонов | Window.FrameMetrics P95 | Пропуски дедлайна приложением |
| --- | ---: | ---: | ---: |
| Обычный текст | 60,04–60,13 FPS | первый прогон 18,34 мс, два следующих 4,23–5,02 мс | первый прогон 1, два следующих 0 |
| Сложный Markdown | 60,00–60,05 FPS | 4,68–5,02 мс | 0 |
| Сложный Markdown + обновления | 59,32–59,75 FPS | 4,53–5,34 мс | 0 |

В контрольных прогонах не воспроизвелись длинные кадры в сотни миллисекунд; P95 интервала представления 17,87–18,97 мс. У всех прогонов
FrameMetrics dropped reports равны 0. Результаты поддерживают вывод, что **контроль окружения существенно влияет на измерения Android-эмулятора**,
но несколько переменных окружения менялись вместе, поэтому нельзя объявить конкретную задачу GMS единственной причиной
и тем более заявить, что оптимизация приложения устранила прежние длинные кадры. Исходные аномальные прогоны сохранены.

## Порядок следующей оптимизации

1. **Разностная перерисовка iOS реализована.** Изменения данных/ширины идут через diffable; окружение и захваты обычных значений распространяются через
   живой SwiftUI wrapper, а не через переконфигурацию всех видимых строк при обновлении сообщения. Новые регрессии сохраняются.
2. **iOS: уменьшить повторные измерения сложных строк.** В первую очередь переиспользовать renderer-ready контент и hosting-конфигурацию;
   оценить кеш измерений по версии контента, ширине и шрифту. При изменении высоты асинхронными изображениями, раскрытым состоянием, подсветкой кода
   он обязан инвалидироваться. Для более длинного Markdown можно оценить виртуализацию по блокам; не переписывайте сперва индекс списка, который уже является бинарным поиском.
3. **Android: сначала установить причину первого/спорадических длинных кадров.** С учётом планирования, RenderThread/GPU, холодного/тёплого кеша
   решать про Baseline Profile, кеш раскладки текста или предзагрузку сложных строк. Текущих результатов недостаточно для выводов
   «переписать LazyColumn заново» или «полные кадры стабильно достигнуты».
4. В последующих приёмках добавить реальные жесты iOS / быстрый fling / коммит страниц / изображения / клавиатуру, и в конце сравнить на реальном устройстве
   в release/profile-сборке P95/P99, пропуски дедлайна, память; не делать FPS симулятора CI-гейтом.
