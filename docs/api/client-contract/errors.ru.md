# Ошибки

Семантика ошибок для всех эндпоинтов `/api/*`. Опирается на `hub/src/web/routes/guards.ts` и отдельные файлы маршрутов в `hub/src/web/routes/`; эталонный потребитель — `web/src/api/client.ts` (`ApiError`, `parseErrorCode`).

## Форма тела

Ответы с ошибками — JSON:

```json
{ "error": "Session is inactive", "code": "session_inactive" }
```

- `error` — понятное человеку сообщение. **Никогда не сопоставляйте по нему**: потребители локализуют его, а хаб может переформулировать (это правило сформулировано в самом `guards.ts`).
- `code` — необязательный стабильный машинно-читаемый дискриминатор. Клиенты ветвятся по `(status, code)`.
- `issues` — присутствует в некоторых 400: детали валидации Zod (вывод `parsed.error.issues` или `.flatten()`). Полезно для логов, не для ветвления.
- Некоторые эндпоинты добавляют контекстные поля (например, экспорт с 413 добавляет `count`/`limit`; reopen с 422 добавляет `missing[]`).

Когда `code` отсутствует, ветвитесь только по статусу и обрабатывайте сбой обобщённо. Веб-эталон при отсутствии `code` использует `error` как псевдокод (`parseErrorCode`) — это допустимо для логов, но не для логики.

## Эндпоинты в обёртке RPC

Многие эндпоинты отвечают не из состояния хаба — хаб передаёт запрос по Socket.IO в CLI-процесс сессии (или раннер машины) и пересылает результат: git/файлы/каталоги/поиск, сгенерированные изображения, загрузки, каталоги моделей, доступность агентов, slash-команды, навыки, spawn, list-directory, paths/exists. (Эндпоинты конфигурации режима/модели/усилия тоже на RPC, но отображают сбои применения в 409 с сообщением.) Их режимы сбоев отличаются от обычных эндпоинтов:

1. **CLI доступен, команда не выполнена** → HTTP **200** с `{success: false, error}` (например, `runRpc` в `hub/src/web/routes/git.ts` перехватывает ошибки RPC, включая 30-секундный таймаут RPC, и возвращает их в JSON-конверте). Клиенты должны проверять поле `success` в каждом ответе RPC-формы; HTTP 200 сам по себе ничего не значит.
2. **CLI офлайн / обработчик отсутствует** → зависит от маршрута: маршруты каталогов моделей в `machines.ts` отображают `RpcTargetMissingError` в **503 `rpc_target_missing`**; маршруты в стиле `git.ts` сворачивают это в конверт 200 `{success: false}`; resume/reopen показывают **503 `no_machine_online`**.
3. **Подсистемы хаба не подняты** → **503 `Not connected`** из `requireSyncEngine` (краткое окно запуска/остановки).

Явные сбои `rpc_target_missing` / `no_machine_online` означают, что хост
выполнения или обработчик недоступны. Не выводите это только из `success: false`:
доступный CLI может сообщить о сбое команды, пути, разрешения или валидации.
Сохраните эту ошибку для отображения; успех HTTP — не успех операции.

Один маршрут уточняет это правило. `GET /api/machines/:id/agy-models` продолжает отдавать последний каталог, который машина получила из `agy models`, пока CLI перепроверяет его в фоне, поэтому он может ответить `success: true` **и** нести `error`: список пригоден, а `error` объясняет, почему он может быть устаревшим (обычно истёк вход в agy на машине). Отображайте его рядом с каталогом, а не вместо него, и предлагайте `?refresh=true` как способ запросить снова — обычный повтор отвечается из того же кеша.

Когда эта фоновая перепроверка даёт другой список, машина сообщает об этом через существующий поток событий, а не заставляет клиентов спрашивать: `machine-agy-models-updated` (см. [SSE](./sse.ru.md)) несёт только `machineId`. Перезапросите по нему маршрут этой машины — ответ берётся из кеша машины, поэтому он не стоит запуска `agy` и не порождает дальнейших событий. Событие испускается всякий раз, когда перепроверка меняет то, что ответил бы этот маршрут, — другой список **или** появившееся/исчезнувшее предупреждение о входе, — и не испускается, когда не меняется ни то, ни другое, поэтому неудачная перепроверка, поднявшая предупреждение, всё же объявляет о себе. Самый первый список машины никогда не объявляется: тот, кто его вызвал, уже его ждёт. Запросы в этом окне отвечаются из кеша машины и не запускают agy.

## Рекомендации по повторам

| Класс | Повторять? |
|-------|------------|
| 400 / 403 / 404 / 409 / 413 / 422 | Нет (исправьте ввод, обновите состояние или скройте интерфейс) |
| 401 (middleware) | Один раз, после тихой повторной аутентификации ([Auth](./auth.ru.md#тихая-повторная-аутентификация-обработка-401)) |
| 429 / 502 / 503 | Чтения: повторять с backoff. Мутации: следуйте контракту восстановления эндпоинта; не воспроизводите запись с неизвестным результатом |
| 200 `{success: false}` | Изучите ошибку и контракт эндпоинта; ручной повтор только когда это безопасно. Этот конверт также может означать отсутствующую цель RPC или таймаут |
