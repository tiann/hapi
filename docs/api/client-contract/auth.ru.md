# Аутентификация и сопряжение

Как нативный клиент получает и поддерживает учётные данные для одного хаба. Клиент может быть сопряжён с несколькими хабами; всё ниже — **на каждый URL хаба**.

## Модель учётных данных

Источник истины: `hub/src/config/cliApiToken.ts`, `hub/src/web/routes/auth.ts`.

| Учётные данные | Срок жизни | Откуда берутся | Для чего |
|----------------|-----------|----------------|----------|
| **Токен доступа** | Долгоживущий (пока оператор не сменит `CLI_API_TOKEN`) | QR-код/диплинк сопряжения или ручной ввод | Обменивается на JWT через `POST /api/auth`; долговечный секрет клиента |
| **JWT** | 4 часа | Ответ `POST /api/auth` | `Authorization: Bearer` в каждом запросе `/api/*` |

Базовый токен хаба (`CLI_API_TOKEN`) автоматически генерируется при первом запуске (32 случайных байта, base64url, ~43 символа) и сохраняется в `settings.json` хаба; заданный оператором env-токен переопределяет его. Настроенный базовый токен никогда не содержит `:` — иначе хаб отказывается запускаться (`validateCliApiToken`).

## Сопряжение

Источник истины: `hub/src/startHub.ts`, `web/src/components/settings/CompanionPairing.tsx`.

Терминал хаба (при запуске с `--relay`) печатает два QR-кода; экран веб-приложения Настройки → Companion pairing отображает второй из них:

| QR | Формат | Параметры |
|----|--------|-----------|
| Прямой веб-доступ | `https://app.hapi.run/?hub=<url>&token=<accessToken>` | `hub`, `token` |
| Диплинк компаньона | `hapicompanion://bind?hub=<url>&code=<accessToken>` | `hub`, `code` |

Нативные клиенты регистрируют схему `hapicompanion://` и разбирают ссылки `bind`: `hub` — базовый URL хаба, `code` — токен доступа. Обратите внимание на несовпадение имён параметров: веб-QR несёт то же значение в `token=`, диплинк компаньона — в `code=`. Надёжный сканер может принимать обе формы; форма диплинка канонична для нативных приложений. Всегда предусматривайте ручной запасной вариант (ввод URL хаба + токена доступа) для локальных хабов без `--relay`.

Оба приложения из репозитория принимают обе формы QR во встроенных сканерах. Android
требует HTTPS для URL хаба и веб-QR и отключает незашифрованный трафик в
манифесте. iOS разбирает HTTP- и HTTPS-URL, но транспорт остаётся подчинён
системной сетевой политике; в его проекте нет исключений ATS. Используйте HTTPS
в примерах сопряжения. См. [Нативные приложения → Сопряжение](../../guide/native-apps.md#pair-with-your-hub) (англ.).

Оба приложения нормализуют идентичность хаба к `scheme://host[:port]`, приводя
схему/хост к нижнему регистру и удаляя порты по умолчанию, пути, запросы и фрагменты.
Обратные прокси должны предоставлять хаб по этому origin, а не только под префиксом пути.
Источники: iOS `HapiClient/Auth/HubRegistry.swift` (`HubURLNormalization`),
Android `core/data/.../auth/HubUrls.kt` и `core/protocol/.../pairing/PairingLinks.kt`.

## Грамматика токена доступа

Источник истины: `hub/src/utils/accessToken.ts`.

```
accessToken = base [":" namespace]
```

- Разделение по **последнему** `:`. Нет двоеточия → пространство имён по умолчанию `"default"`.
- После разделения обе части должны быть непустыми и не содержать ведущих/замыкающих пробелов, иначе токен недействителен.
- Весь ввод обрезается по краям перед разбором.

Клиенты должны считать токен доступа **непрозрачной строкой** и передавать его без изменений в `POST /api/auth` — никогда не разделяйте его на стороне клиента, чтобы «нормализовать». Разделение выполняет хаб; часть с пространством имён определяет, какие сессии увидит полученный JWT (см. [Пространства имён](#пространства-имён)).

## Обмен токена

Источник истины: `hub/src/web/routes/auth.ts`.

```
POST /api/auth
Content-Type: application/json

{ "accessToken": "<code from pairing>" }
```

Успех (200):

```json
{
  "token": "<JWT>",
  "user": { "id": 1, "firstName": "Web User" }
}
```

Ошибки: `400 {"error": "Invalid body"}`, `401 {"error": "Invalid access token"}`. Схема запроса: `AuthRequestSchema` в `shared/src/apiTypes.ts` (вариант `initData` — только для Telegram).

`POST /api/bind` (`hub/src/web/routes/bind.ts`) — **только для Telegram**: он привязывает личность Telegram к пространству имён и требует Telegram `initData`. Нативные клиенты его никогда не вызывают.

## JWT

Источник истины: `hub/src/web/routes/auth.ts` (подпись), `hub/src/web/middleware/auth.ts` (проверка), `hub/src/config/jwtSecret.ts` (ключ).

- HS256, подписывается локальным для хаба 32-байтовым секретом (`<dataDir>/jwt-secret.json`).
- Полезная нагрузка: `{ "uid": <number>, "ns": <string> }` плюс стандартные `iat`/`exp`.
- **Истекает через 4 часа** после выпуска.

Для целей аутентификации считайте токен непрозрачным, но клиенты могут декодировать полезную нагрузку base64url, чтобы прочитать `exp` и заранее запланировать обновление (веб-клиент делает именно это — `decodeJwtExpMs` в `web/src/hooks/useAuth.ts`).

## Отправка токена

Источник истины: `hub/src/web/middleware/auth.ts`.

- Каждый запрос `/api/*`: `Authorization: Bearer <JWT>`.
- Исключения: `/api/auth` и `/api/bind` не требуют аутентификации; `GET /health` вне `/api` и без аутентификации.
- `GET /api/events` (SSE) **дополнительно** принимает `?token=<JWT>` как query-параметр — для HTTP-стеков, чей EventSource не может задавать заголовки. При наличии обоих побеждает заголовок. Никакой другой эндпоинт не принимает аутентификацию через query-параметр.

## Тихая повторная аутентификация (обработка 401)

Нативные реализации: iOS `HapiClient/Auth/AuthManager.swift` и
`HapiClient/APIClient.swift`; Android `core/data/.../auth/TokenAuthenticator.kt`.
Веб-эталон: `web/src/api/client.ts` (`request()`),
`web/src/hooks/useAuth.ts` (`refreshAuth`).

JWT истекает каждые 4 часа, поэтому 401 — рутина, а не исключение. Контракт:

1. При 401 от аутентифицированного клиентского API-запроса повторно обменяйте **сохранённый токен доступа** через `POST /api/auth`. Сам обмен аутентификации не должен входить в этот цикл.
2. Если обмен успешен, повторите исходный запрос **ровно один раз** с новым JWT.
3. 401 от обмена или ещё один 401 при повторном запросе — терминально: требуется повторное сопряжение. Обмен, отклонённый с 401, означает, что сохранённый токен доступа недействителен или отозван.
4. Временный сбой обмена (сетевая ошибка или 5xx) приводит к сбою вызова без выхода из аккаунта и удаления сопряжённых учётных данных. Восстановитесь при возврате связи; не считайте каждую ошибку обновления отзывом токена.

Замечания по реализации:

- **Single-flight** для обновления: параллельные 401 разделяют один обмен или переиспользуют JWT, уже обновлённый другим вызывающим. Оба нативных клиента реализуют это.
- Оба нативных клиента заранее обновляют токен в течение 10 минут до истечения. iOS может сохранить ещё действительный кешированный JWT после неудачного упреждающего обновления и ограничивает такие попытки на 15 с. Android обновляет токен до подключения SSE и оставляет временные сбои восстановимыми.
- Веб планирует упреждающее обновление за 60 с до `exp` и при выходе на передний план, когда оставшийся TTL < 60 с. Эти решения о планировании — детали реализации клиента, а не дополнительные требования к версии протокола. SSE аутентифицируется в момент подключения, поэтому переподключениям нужен актуальный токен.

## Пространства имён

Источник истины: `hub/src/web/middleware/auth.ts` (устанавливает `namespace` из `ns`), `hub/src/web/routes/guards.ts`, `hub/src/web/routes/{usage,storage,hubSettings,voice}.ts`.

Каждый запрос выполняется в пространстве имён JWT (утверждение `ns`, производное от суффикса токена доступа). Сессии и машины привязаны к пространству имён: сессия из другого пространства имён отвечает `403 Session access denied` / `404 Session not found` согласно логике guard.

`ns === "default"` — это **владелец хаба**. Интерфейсы только для владельца (403 для любого другого пространства имён):

| Эндпоинт | Проверка |
|----------|----------|
| `GET /api/usage/summary` | `hub/src/web/routes/usage.ts` |
| `GET /api/storage/sqlite` | `hub/src/web/routes/storage.ts` |
| `PUT /api/hub-settings` (запись; чтение открыто для всех пространств имён) | `hub/src/web/routes/hubSettings.ts` |
| `GET`/`PUT /api/voice/transcription/credentials` | `hub/src/web/routes/voice.ts` |

Оба нативных приложения открывают экраны использования/хранилища только при
утверждении `ns` аутентифицированного JWT, равном `default`, и скрывают их иначе;
отсутствие утверждений приводит к отказу. Передавайте токен доступа при
аутентификации без изменений, а не переписывайте его суффикс пространства имён.
Хаб остаётся авторитетным для каждого запроса только для владельца.

## Рекомендации по хранению учётных данных

- Храните **токен доступа** в защищённом платформой хранилище: iOS Keychain, Android `EncryptedSharedPreferences` (за интерфейсом, чтобы механизм можно было заменить). Никогда не в обычных файлах и не в логах.
- Храните учётные данные **на каждый базовый URL хаба** (нормализованный), так как клиент может быть сопряжён с несколькими хабами. Веб-эталон: ключ localStorage `hapi_access_token::<baseUrl>` (`web/src/hooks/useAuth.ts`, `web/src/components/settings/CompanionPairing.tsx`).
- JWT — чувствительные bearer-учётные данные, но их не обязательно сохранять: держите в памяти и обменивайте заново при холодном старте. Если сохраняете (чтобы сэкономить один round-trip при запуске), храните рядом с токеном доступа с той же защитой.
- При отмене сопряжения/выходе: удалите оба учётных данных и сначала отмените регистрацию нативного push (`DELETE /api/devices/register`), пока у вас ещё есть действительный JWT.

## Тела ошибок 401 {#401-error-bodies}

Все — JSON со строкой `error`; ни у одного нет поля `code`, кроме Telegram `not_bound` (использует `error` как дискриминатор — нативные приложения его не видят):

| Источник | Тело | Значение |
|----------|------|----------|
| Middleware, любой `/api/*` | `{"error": "Missing authorization token"}` | Нет bearer-заголовка (и нет `?token=` для `/api/events`) |
| Middleware, любой `/api/*` | `{"error": "Invalid token"}` | Проверка подписи/срока JWT не удалась → запустите тихую повторную аутентификацию |
| Middleware, любой `/api/*` | `{"error": "Invalid token payload"}` | JWT действителен, но полезная нагрузка не `{uid, ns}` (чужой/устаревший токен) |
| `POST /api/auth` | `{"error": "Invalid access token"}` | Токен доступа неверен или сменён → требуется повторное сопряжение |
| `POST /api/auth` (путь Telegram) | `{"error": "not_bound"}` | Только для Telegram; недостижимо при аутентификации через `accessToken` |

Цикл повторной аутентификации должен отличать 401 от middleware (восстановимо через повторный обмен) от 401 от `/api/auth` (терминально — не зацикливайтесь).
