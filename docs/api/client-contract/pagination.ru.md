# Пагинация сообщений, окно и оптимистичная отправка

**Аудитория:** разработчики нативных клиентов HAPI (iOS / Android). Эта страница описывает протокол постраничного чтения сообщений (`GET /api/sessions/:id/messages`), контракт сброса эпохи, цикл синхронизации хвоста, рекомендуемое клиентское окно и жизненный цикл оптимистичной отправки/отмены. Смежные страницы: [sse](./sse.ru.md), [messages](./messages.ru.md), [rest](./rest.ru.md).

Источник истины: `shared/src/apiTypes.ts` (`MessagesQuerySchema`, `MessagesResponse`, `SendMessageRequestSchema`), `hub/src/web/routes/messages.ts`, `hub/src/sync/messageService.ts`, `hub/src/store/messages.ts`, эталонный клиент `web/src/lib/message-window-store.ts` + `web/src/lib/messages.ts`.

---

## Ключ позиции

Сообщения упорядочены по **составной позиции**, а не только по `seq`:

```
position = (at, seq)   where at = invokedAt ?? createdAt
```

По возрастанию `at`, при равенстве — по `seq`. Обоснование: сообщение пользователя в очереди сидит на своём `createdAt`, пока агент его не потребит, тогда проставляется `invokedAt` и строка **перемещается вперёд** на позицию вызова. Один лишь `seq` (счётчик вставок на сессию) заморозил бы строки очереди в порядке постановки. Поэтому каждый курсор в этом протоколе — это **пара** `(seq, at)`; обе половины всегда требуются вместе.

## `GET /api/sessions/:id/messages`

Query-параметры (`MessagesQuerySchema`; все числа приводятся из строк):

| Параметр | Тип | Ограничение |
|---|---|---|
| `limit` | int | 1–200. **По умолчанию 50**, если опущен; веб-эталон использует 200 для полных страниц latest/reset, after и before, и 20 для первого обновления хвоста при повторном входе в кешированную сессию. |
| `beforeSeq` + `beforeAt` | int + int | Страница строго старше этой позиции. Требуются парой. |
| `afterSeq` + `afterAt` | int + int | Страница строго новее этой позиции. Требуются парой. |
| `untilSeq` + `untilAt` | int + int | Включающая голова снимка для цикла догона. Требуются парой; **требует курсора `after`**. |
| `epoch` | int ≥ 0 | Кешированная эпоха клиента. **Требует курсора `after`.** |

Правила валидации (нарушения — `400 {"error":"Invalid query","issues":…}`):

- `beforeAt`⇄`beforeSeq`, `afterAt`⇄`afterSeq`, `untilAt`⇄`untilSeq` должны передаваться вместе.
- `before` и `after` **взаимоисключающие**.
- `until` и `epoch` допустимы только вместе с `after`.

Ошибки сессии: `404` не найдена, `403` чужое пространство имён (см. [errors](./errors.ru.md)).

### Форма ответа

```ts
type MessagesResponse = {
  messages: DecryptedMessage[]          // ascending display order
  page: {
    direction: 'latest' | 'before' | 'after'
    limit: number
    epoch: number                       // server's current epoch for this session
    reset: boolean                      // true ⇒ discard your window, this page replaces it
    nextBeforeSeq: number | null        // cursor for the next OLDER page
    nextBeforeAt: number | null
    nextAfterSeq: number | null         // cursor for the next NEWER page
    nextAfterAt: number | null
    snapshotHeadSeq: number | null      // newest position at snapshot time
    snapshotHeadAt: number | null
    hasMore: boolean                    // more rows exist in the requested direction
  }
}
```

### `latest` (без курсора)

Новейшие `limit` строк по позиции, **плюс** — вне полосы — каждое невызванное локальное сообщение пользователя (строки очереди, включая запланированные на будущее), чтобы свежий клиент всё равно видел панель очереди, даже когда эти строки выпадают из страницы. Внеполосные строки прикрепляются к каждому ответу latest и **не** влияют на курсор: `nextBefore*` привязан к самой старой строке упорядоченной по позиции страницы как таковой. `hasMore` = существует хотя бы одна строка до неё. Если страница содержит только отфильтрованные на стороне сервера строки (см. [messages](./messages.ru.md)), хаб автоматически переходит к более старым страницам, пока не вернёт что-то или не исчерпает историю.

### `before`

Строки строго старше курсора. `nextBefore*` = самая старая строка этой страницы; `hasMore` = есть хотя бы одна строка старше неё. Ответ также несёт текущий `epoch` — сравните его с кешированным (см. ниже).

### `after`

Строки строго новее курсора, ограниченные **включающей головой снимка** = `min(until, currentHead)` (или тем, что существует). Это не даёт циклу догона гнаться за сообщениями, добавленными во время его работы. Ответы:

- `epoch` клиента ≠ эпоха сервера ⇒ сервер игнорирует курсор и возвращает **страницу latest с `reset: true`** (`direction: 'latest'`).
- Голова снимка ≤ курсора ⇒ пустая страница, `hasMore: false`, `nextAfter*` повторяет курсор.
- Иначе: `nextAfter*` = позиция последней строки, `hasMore` = `nextAfter < snapshotHead`.

## Эпоха

`epoch` — монотонный счётчик на сессию (таблица `message_epochs`, начинается с 0), который увеличивается всякий раз, когда история меняется так, что составные курсоры становятся недействительными (`hub/src/store/messages.ts`):

- новая строка попадает **до** текущей головной позиции (вставка не по порядку, например импорт транскрипта с более ранней меткой времени);
- сообщение очереди удаляется (отмена);
- rewind / замена истории (`replaceSessionMessagesFrom`);
- сообщения копируются/сливаются между сессиями (обе стороны), гидратация fork.

Контракт клиента:

- **Запрос `after`** — всегда отправляйте кешированный `epoch`. При несовпадении сервер отвечает страницей latest с `reset: true`; **отбросьте всё локальное окно** и замените его этой страницей.
- **Запрос `before`** — `page.epoch` в ответе может отличаться от кешированного; если так, ваши курсоры бессмысленны: сбросьте состояние курсоров, пометьте окно на сброс latest и выполните свежую синхронизацию хвоста (веб: `fetchOlderMessages` → исход `epoch-reset`).
- О структурном изменении также объявляется в реальном времени через SSE-событие `messages-invalidated` — для открытой сессии очистите окно и синхронизируйте хвост с нуля.

## Цикл синхронизации хвоста

Запускайте после подключения, после рукопожатия SSE `resume: 'gap'`, при открытии сессии и по команде (`messages-invalidated`). Эталон: `runTailSync` в `web/src/lib/message-window-store.ts`.

1. **Нет пригодного состояния** (нет новейшего курсора, нет кешированной эпохи или ожидается сброс):
   - Для действительно холодного окна без курсора и без ожидающего структурного сброса запросите `GET …/messages?limit=20` (latest), чтобы новейшее пригодное содержимое разговора быстро отрисовалось.
   - Для ожидающего структурного сброса запросите обычную полную страницу latest с `limit=200`.
   - Замените/слите в окно, сохраните `page.epoch`, `nextBefore*` (курсор более старой страницы) и `snapshotHead*` (новейший курсор). Готово.
2. **Повторный вход в кешированную сессию с пригодным курсором**: `GET …/messages?limit=20` (latest), замените устаревшее серверное окно, сохранив строки очереди/параллельные, затем предоставьте `nextBefore*` для загрузки старой истории. Готово.
3. **Есть курсор + эпоха вне активации**: цикл
   - `GET …/messages?afterSeq&afterAt&epoch[&untilSeq&untilAt]&limit=200`, где `after` начинается с вашего новейшего курсора, а `until` — это `snapshotHead*`, зафиксированный из **первого** ответа цикла (фиксирует цель, чтобы цикл завершился).
   - `page.reset` или `direction: 'latest'` ⇒ замените окно этой страницей; остановитесь.
   - Иначе слейте строки, продвиньте `after = nextAfter*`, обновите новейший курсор до `max(current, nextAfter)`; остановитесь, когда `hasMore` равно false.
   - Защита: если `nextAfter` не продвинулся за предыдущий курсор, прервите с ошибкой (нарушение протокола, не крутитесь).

Новые живые строки продолжают приходить через SSE-событие `message-received`; поглощайте их и продвигайте новейший курсор до `max(current, incoming position)`. Запускайте только одну синхронизацию хвоста за раз на сессию; если события вынуждают ещё одну (например, посреди цикла пометили сброс), поставьте в очередь завершающий прогон.

## Клиентское окно (нормативная рекомендация)

Константы из веб-эталона (`web/src/lib/message-window-store.ts`):

| Константа | Значение | Значение |
|---|---|---|
| `INITIAL_PAGE_SIZE` | 20 | Размер запроса для холодной страницы latest, чтобы приоритизировать первую отрисовку. |
| `PAGE_SIZE` | 200 | Размер запроса для обычных latest/reset, вперёд и старых страниц. |
| `CACHED_REENTRY_PAGE_SIZE` | 20 | Первая страница хвоста latest при повторном входе в кешированную сессию. |
| `VISIBLE_WINDOW_SIZE` | 400 | Макс. обычных строк в режиме **хвоста** (следование за живым низом). |
| `HISTORY_WINDOW_SIZE` | 600 | Макс. обычных строк в режиме **истории** (пользователь отмотал назад). |
| `OLDER_LOAD_WINDOW_SIZE` | 800 | Временный лимит, пока сливается старая страница (prepend). |
| `AGENT_RUN_WINDOW_SIZE` | 800 | Отдельная корзина обрезки для строк codex `agent-run-*`, чтобы следы фоновых агентов не вытесняли чат. |

Правила:

- Режим **хвоста** обрезает сверху (самые старые отбрасываются). Отбрасывание строк ⇒ установите `hasMore: true` и пересчитайте курсор старой страницы от самой старой сохранённой строки.
- Режим **истории** обрезает снизу (самые новые отбрасываются). Отбрасывание новейших строк означает, что ваше окно больше не достигает хвоста ⇒ пометьте «требуется сброс latest»: при возврате в режим хвоста отбросьте курсоры и запросите свежую страницу latest, а не доверяйте устаревшим.
- **Строки очереди никогда не обрезаются** (сообщения пользователя с `invokedAt === null`, см. ниже) — они заново сливаются после каждой обрезки.
- Сохраняйте окно (сообщения + курсоры + эпоху) на сессию для мгновенной отрисовки при холодном старте; действительно холодное окно и повторная активация из кеша запрашивают небольшую страницу latest для первой отрисовки, а структурные сбросы запрашивают обычную полную страницу latest и согласуются. Другой клиент мог продвинуть сессию на много страниц вперёд; повторная активация из кеша сохраняет возвращённый старый курсор доступным для загрузки истории по требованию.

## Оптимистичная отправка

Отправка: `POST /api/sessions/:id/messages` (ограничения ниже). Эталон: `web/src/hooks/mutations/useSendMessage.ts`, `mergeMessages` в `web/src/lib/messages.ts`.

Жизненный цикл:

1. Сгенерируйте клиентский `localId` и добавьте **оптимистичную строку**: `{id: localId, seq: null, localId, invokedAt: null, scheduledAt, createdAt: now, status:'sending', content: {role:'user', content:{type:'text', text, attachments?}, meta:{deliveryMode}}}`. Строка *оптимистична* тогда и только тогда, когда `id === localId`.
2. При успехе POST: статус → `queued`, если сессия сейчас думает, иначе `sent`. При сбое: удалите строку и восстановите поле ввода (или оставьте её как `failed` с возможностью повтора, когда есть вложения).
3. **Эхо**: хаб испускает `message-received` с сохранённой строкой (серверный `id`, настоящий `seq`, тот же `localId`). Слияние сохранённой строки, чей `localId` совпадает с оптимистичной, **заменяет** оптимистичную, сохраняя клиентский `status` и уже известный `invokedAt`, которого нет у серверной строки. Запасной вариант, когда эхо `localId` не совпало: удалите оптимистичную строку `sent`, когда серверное сообщение пользователя появляется в пределах **10 с** на той же позиции.
4. **`messages-consumed {localIds, invokedAt}`** (SSE): проставьте `invokedAt` и переключите статус на `sent` у совпадающих строк (пропуская `failed`). Именно это переносит сообщение из панели очереди в обсуждение на позицию вызова.
5. **`messages-indeterminate {localIds}`** (SSE): у нативной отправки или мутации очереди неизвестный результат. Оставьте `invokedAt: null`, пометьте `deliveryState:'indeterminate'` и исключите строку из автоматического воспроизведения. Retry/Cancel — явные действия разрешения и могут оставаться недоступными, пока нативный результат не удастся согласовать.
6. **`messages-requeued {localIds}`** (SSE): явный Retry восстановил нормальную доставку очереди; очистите `deliveryState`.
7. **`message-cancelled {messageId, localId?}`** (SSE): удалите строку (совпадение по любому id).

**Семантика очереди**: сообщение пользователя «в очереди» тогда и только тогда, когда `invokedAt === null` **строго**, `deliveryState !== 'indeterminate'` и `status !== 'failed'`. Неопределённая строка остаётся видимой в панели неразрешённой доставки, но не подлежит автоматической доставке. `undefined` означает уже вызвано (строки из хабов до V8 опускают поле) — в панель очереди попадают только строки, явно несущие `null`. На стороне сервера строки, отправленные без `localId`, помечаются вызванными при вставке и никогда не могут попасть в очередь.

### Восстановление состояния очереди

После переподключения, чьё рукопожатие сказало `resume: 'gap'` (рукопожатие `ok` уже воспроизвело события consume/cancel), события consumed/cancelled для ваших строк очереди могли быть потеряны. Эталон: `web/src/lib/queued-state-reconciliation.ts`.

1. Завершите синхронизацию хвоста.
2. Соберите кандидатов `localId`: строки пользователя с `invokedAt === null`, исключая оптимистичные строки, всё ещё `sending`/`failed`.
3. `POST /api/sessions/:id/messages/queued-state` с `{"localIds": […]}` (не более 1000 за вызов; больше — пакетами) → `{queuedLocalIds: string[], indeterminateLocalIds: string[], invokedLocalMessages: [{localId, invokedAt}]}`.
4. Примените `invokedLocalMessages` точно как `messages-consumed`; пометьте `indeterminateLocalIds` как неразрешённую доставку. Сохраните и строки очереди, и неопределённые; удаляйте только кандидатов, отсутствующих во **всех трёх** группах результата. Нативная отправка в процессе сообщается как неопределённая, а не как удалённое сообщение.

## Ограничения отправки

Тело `POST /api/sessions/:id/messages` (`SendMessageRequestSchema`):

| Поле | Тип | Правила |
|---|---|---|
| `text` | string | Обязательно (маршрут также принимает пустой текст, когда `attachments` непусто). |
| `localId` | string | Необязательно, но **обязательно для `scheduledAt`**, и на практике нужно: без него строка помечается вызванной при вставке (нет пути очередь/ack/отмена). |
| `attachments` | `AttachmentMetadata[]` | Необязательно. Не допускается с `scheduledAt`. |
| `scheduledAt` | epoch ms | Необязательно. Должно быть ≤ сейчас + **7 дней**; требует `localId`; без вложений; никогда не `steer`. |
| `deliveryMode` | `'queue'` \| `'steer'` | Необязательно, по умолчанию `queue`. `steer` соблюдается только для сессий **flavor Pi** и никогда для запланированных отправок — хаб молча нормализует всё остальное к `queue`, а отложенная/воспроизведённая доставка (добор после переподключения, повторы, высвобождение по расписанию) всегда понижает `steer` до `queue`. |

Ответ `{"ok": true}`. Отправка в неактивную сессию возвращает `409 {"error":"Session is inactive","code":"session_inactive"}` — сначала resume/reopen, и учтите, что возобновлённая сессия **может иметь другой id** (перенесите черновики и перецельтесь, см. [rest](./rest.ru.md)).

## Отмена и steer

**Отмена**: `DELETE /api/sessions/:id/messages/:messageId` — `:messageId` может быть серверным id **или** `localId`. Объединение ответов (`CancelMessageResponseSchema`):

| Ответ | Значение | Действие клиента |
|---|---|---|
| `{"status":"cancelled","localId":string\|null}` | Строка удалена (или уже исчезла). Увеличивает эпоху. | Удалить строку. |
| `{"status":"invoked","message":DecryptedMessage}` | Слишком поздно — агент потребил её до того, как отмена пришла. | **Поглотите возвращённое сообщение** как авторитетную строку (правильный `invokedAt`, статус `sent`); не воскрешайте снимок очереди. |
| `{"status":"busy","localId":string}` | Нативная доставка/удаление не разрешены; отмену нельзя подтвердить. | Восстановите строку как неопределённую; согласуйте состояние очереди, прежде чем разрешать Retry/Cancel. |

Другие подписчики узнают тот же результат через SSE-события `message-cancelled` / `messages-consumed`.

**Направить сообщение очереди в текущий ход**: `POST /api/sessions/:id/messages/:messageId/steer` → `SteerQueuedMessageResponseSchema`. В отличие от опции `deliveryMode` при отправке, этот эндпоинт поддерживает сессии Pi, Codex и Cursor ACP (`isSteeringSupportedForSession` в `shared/src/modes.ts`). Он отклоняет все запланированные сообщения и отклоняет сессии под управлением терминала, если они не объявляют `concurrentClients`.

| Ответ | Действие клиента |
|---|---|
| `{"status":"steered","localId"}` | Оставьте строку на стороне очереди; она вклинивается в живой ход. |
| `{"status":"invoked","message"}` | Уже потреблено — поглотите сообщение. |
| `{"status":"failed","error","localId":string\|null}` | Покажите ошибку. Не выводите состояние доставки только из этого; согласуйте, прежде чем повторять, когда нативный результат неизвестен. |

**Повтор неопределённой доставки**: `POST /api/sessions/:id/messages/:messageId/retry`
инициируется только пользователем. `retried` или `already-queued` означает нормальную
доставку очереди; `invoked` несёт авторитетное сообщение; `not-found` означает, что
строка исчезла. `retry-unavailable` оставляет строку неразрешённой: хаб не смог доказать,
что повтор позволит избежать дублирования работы. Согласуйте вместо автоматического повтора.
