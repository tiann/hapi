# Контракт нативного клиента

**Аудитория:** разработчики нативных клиентов HAPI — приложения iOS (`ios/`), Android (`android/`) и любого другого не-веб клиента, работающего с клиентским API хаба. Эти страницы — основной источник спецификации для такой работы: каждое утверждение опирается на исходный код хаба/веба, а каждый раздел называет свой исходный файл, чтобы разработчики (люди или ИИ-агенты) могли сверить его с кодом.

**Область:** HTTP-контракт между клиентом и одним хабом — сопряжение и аутентификация, REST-эндпоинты, поток SSE, пагинация сообщений, декодирование сообщений и семантика ошибок. Основные функции сессий/чата используют **REST + SSE**. Веб-терминалы дополнительно используют JWT-аутентифицированное пространство имён Socket.IO `/terminal`, выходящее за рамки этого контракта; `/cli` — внутреннее пространство имён CLI↔хаб и не является API для нативных клиентов.

Об установке, сопряжении и функциях каждого приложения см.
[руководство по нативным приложениям](../../guide/native-apps.md) (англ.). Задокументированный
здесь эндпоинт не означает, что оба приложения предоставляют соответствующий интерфейс.

## Версионирование

Источник истины: `hub/src/web/server.ts` (маршрут `/health`), `shared/src/version.ts`.

`GET /health` не требует аутентификации и возвращает:

```json
{
  "status": "ok",
  "protocolVersion": 1,
  "capabilities": {
    "workGraph": true,
    "titleSuggestion": false
  }
}
```

- `protocolVersion` — поколение проводного протокола (`PROTOCOL_VERSION` в `shared/src/version.ts`, сейчас `1`), отдельное от версий релизов приложения/хаба. Оба нативных приложения требуют его равенства своей поддерживаемой версии и прекращают сопряжение при любом несовпадении. Источники: iOS `HapiClient/Auth/HubPairingService.swift`; Android `feature/pairing/PairingViewModel.kt`.
- `capabilities` — **аддитивны**: новые функции хаба появляются как новые ключи. Клиенты должны игнорировать неизвестные ключи и считать отсутствующие ключи «не поддерживается». Включайте функции по ключам возможностей, а не по версиям сборки хаба.

## Исполняемая спецификация: эталонные фикстуры

Текст в разделе [Messages](./messages.ru.md) описывает дерево декодирования, но *нормативным* артефактом является `shared/fixtures/` — машинно-сгенерированные эталонные файлы, создаваемые из чат-конвейера веб-реализации (`web/src/chat/`). Протокольный модуль нативного клиента должен воспроизводить эти фикстуры в точности; CI перегенерирует их при любом изменении веб-конвейера, поэтому расхождения обнаруживаются автоматически.

Фикстуры и наборы проверок соответствия для нативных приложений присутствуют в этом
репозитории. Перегенерируйте фикстуры из корня репозитория командой `bun run gen:fixtures`;
никогда не редактируйте сгенерированный JSON вручную. Проверки соответствия см. в README
нативных пакетов. Фикстуры фиксируют декодирование протокола и переходы состояний, а не
визуальное представление или паритет функций между нативными приложениями и вебом.

## Связь с контрактом push-уведомлений для компаньона

[Контракт нативного компаньона](../native-companion-contract.ru.md) описывает
регистрацию устройств Android/iOS (`POST /api/devices/register`), зашифрованные
push-конверты, прямую доставку FCM/APNs и общее push-реле. Нативный
клиент реализует этот контракт для интерактивных функций, а тот контракт —
для фонового push. Там, где они пересекаются (аутентификация, отправка сообщения,
одобрение/отклонение), этот контракт является более подробной спецификацией.
