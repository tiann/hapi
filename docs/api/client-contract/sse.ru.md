# Поток SSE (`GET /api/events`)

**Аудитория:** разработчики нативных клиентов HAPI (iOS / Android). Эта страница описывает поток server-sent-events хаба: модель подписки, кадрирование, протокол возобновления, объединение `SyncEvent` и алгоритм версионированного патча сессии. Смежные страницы: [auth](./auth.ru.md), [REST](./rest.ru.md), [pagination](./pagination.ru.md), [messages](./messages.ru.md).

Источник истины: `hub/src/web/routes/events.ts`, `hub/src/sse/sseManager.ts`, `hub/src/web/sseCompression.ts`, `shared/src/schemas.ts` (`SyncEventSchema`), эталонный клиент `web/src/hooks/useSSE.ts`.

## Эндпоинт

`GET /api/events` — долгоживущий ответ `text/event-stream`.

| Query-параметр | Значения | Примечания |
|---|---|---|
| `token` | JWT | Браузерный `EventSource` не может задавать заголовки, поэтому middleware аутентификации принимает `?token=` **только на этом пути** (`hub/src/web/middleware/auth.ts`). Клиенты, умеющие задавать заголовки, могут вместо этого использовать `Authorization: Bearer`. |
| `all` | `true` \| `1` | Глобальная подписка: все события в пространстве имён токена. |
| `sessionId` | id сессии | Подписка на сессию. |
| `machineId` | id машины | Подписка на машину (веб это не использует). |
| `visibility` | `visible` \| `hidden` | Начальное состояние видимости. Всё, кроме литерала `visible`, считается `hidden` (значение по умолчанию). См. [Видимость](#видимость). |
| `lastEventId` | id события | Курсор возобновления для вручную пересобранных соединений. Стандартный **заголовок запроса `Last-Event-ID` побеждает** этот параметр, когда присутствуют оба (автопереподключающиеся реализации EventSource отправляют заголовок). |

Предварительные проверки, до потока байтов:

| Условие | Ответ |
|---|---|
| Движок синхронизации хаба не готов | `503 {"error":"Not connected"}` |
| `sessionId` неизвестен | `404 {"error":"Session not found"}` |
| `sessionId` в другом пространстве имён | `403 {"error":"Session access denied"}` |
| `machineId` неизвестен / чужое пространство имён | `404` / `403` (тот же шаблон) |

`sessionId` может разрешиться в канонический id (вытесненные/слитые сессии); подписка привязывается к **разрешённому** id.

## Кадрирование

Каждый кадр — стандартное сообщение SSE, чья строка `data:` содержит один JSON-кодированный `SyncEvent`:

```
id: 018f3c2a:412:9b1f00aa
data: {"type":"session-updated","sessionId":"...","data":{...}}
```

- **Широковещательные события** (воспроизведённые и живые) несут поле `id:`.
- **Кадры `connection-changed`, `heartbeat` и `toast` НЕ несут `id`.** Курсоры SSE «липкие»: кадр без `id` должен сохранять ранее виденный id (нативный `EventSource` делает это автоматически; рукописные парсеры должны это воспроизвести). Heartbeat никогда не должен сбрасывать или обнулять ваш курсор.
- Сервер никогда не отправляет `retry:`; политика переподключения полностью на стороне клиента (см. [Политика переподключения](#политика-переподключения-нормативная-рекомендация)).

### Формат id события

`{epoch}:{seq}:{nsTag}` — считайте непрозрачным; сохраняйте и возвращайте его, никогда не интерпретируйте.

| Часть | Значение |
|---|---|
| `epoch` | 8-символьная случайная строка, фиксированная на **процесс** хаба. Курсор из времени до перезапуска хаба никогда не совпадёт. |
| `seq` | Целое, монотонно возрастающее на процесс хаба (общее для всех пространств имён/сессий). |
| `nsTag` | Первые 8 hex-символов `sha256("{epoch}|{namespace}")` — привязывает курсор к пространству имён, в котором он был выдан. |

### Кольцо воспроизведения

Хаб хранит последние **256** широковещательных событий, ограничение — **2 МиБ** JSON (самые старые вытесняются первыми; байтовый лимит всегда сохраняет хотя бы одну запись). Кадры `toast` не записываются (они адресованы видимости, а не широковещательны).

## Рукопожатие и возобновление

При подписке хаб испускает **в этом гарантированном порядке**:

1. `connection-changed` — `{"type":"connection-changed","data":{"status":"connected","subscriptionId":"<uuid>","resume":"ok"|"gap"}}` (без `id`).
2. Воспроизведённые события (каждое со своим `id`), когда `resume` равно `ok`.
3. Живой трафик.

Живые широковещательные события, возникшие пока записывается воспроизведение, ставятся на стороне сервера в очередь и сбрасываются после него, поэтому порядок сохраняется.

| Вердикт `resume` | Значение | Действие клиента |
|---|---|---|
| `ok` | Следующее воспроизведение содержит **каждое** событие, пропущенное с курсора. | Полностью пропустить REST-ресинхронизацию. |
| `gap` (или поле отсутствует — старые хабы) | Хаб не может доказать непрерывность. | Полный перезапрос: список сессий, детали сессии(й), синхронизация хвоста сообщений и согласование состояния очереди для открытой сессии (см. [pagination](./pagination.ru.md#восстановление-состояния-очереди)). |

`gap` возвращается всякий раз, когда: курсор не был отправлен, курсор искажён, `epoch` отличается (хаб перезапущен), `nsTag` отличается (курсор выдан в другом пространстве имён — например, после смены токена на том же хабе), `seq` вне диапазона, или события между курсором и самой старой записью кольца были вытеснены.

### Правила курсора (нормативные)

- Держите один курсор **на набор фильтров подписки** (кортеж `all` / `sessionId` / `machineId` плюс хаб + пространство имён). Никогда не воспроизводите курсор, записанный при другом наборе фильтров — хаб воспроизвёл бы против неверного фильтра, и вердикт `ok` был бы неверным для того, что вы на самом деле пропустили.
- Обновляйте курсор **после** того, как событие надёжно обработано. Если обработка выбрасывает исключение, оставьте курсор позади события, чтобы хаб доставил его снова (доставка не менее одного раза; обработчики должны быть идемпотентны).
- Отправляйте курсор при переподключении через заголовок `Last-Event-ID` или `?lastEventId`.

## Политика переподключения (нормативная рекомендация)

Эти константы взяты из эталонного веб-клиента (`web/src/hooks/useSSE.ts`) и хаба (`hub/src/sse/sseManager.ts`); нативным клиентам следует их принять.

| Константа | Значение | Примечания |
|---|---|---|
| Интервал heartbeat сервера | 30 с | `{"type":"heartbeat","namespace":"…","data":{"timestamp":<ms>}}` |
| Порог устаревания | 90 с | Нет кадров (любых) в течение 90 с ⇒ разорвать и переподключиться. |
| Тик watchdog | 10 с | Интервал проверки устаревания; **пропускать проверки в фоне**. |
| Проверка устаревания при возврате на передний план | 45 с | При выходе приложения на передний план, если последний кадр старше 45 с, переподключиться немедленно (приостановка ОС может убить сокет без единой ошибки; одного пропущенного интервала heartbeat уже достаточно, чтобы не доверять ему). |
| Таймаут подключения | 10 с | Попытка, не достигшая OPEN за 10 с, вероятно, зависла на мёртвом сокете из пула — бросьте её и повторите на новом соединении. |
| Backoff | база 1 с, ×2, лимит 30 с | Задержка для попытки *n* (n ≥ 1) = `min(cap, 1000 · 2^(n-1))`. **Первый повтор — немедленный** (только джиттер). |
| Джиттер | +0–500 мс | Равномерный, добавляется к каждой задержке. |
| Медленный потолок | 300 с после 8 попыток | Хаб, остающийся недоступным, обычно недоступен часами; каждый повтор через реле стоит TLS-рукопожатия. |
| В фоне | отложить повторы | Не планируйте повторы в фоне; переподключайтесь немедленно при выходе на передний план. Сбрасывайте счётчик попыток в 0 при каждом успешном открытии. |

Любой полученный кадр — включая heartbeat — считается активностью для часов устаревания. Не полагайтесь на встроенное автопереподключение платформенной SSE-библиотеки: оно не соблюдёт backoff, отложенность в фоне или таймаут подключения.

## Модель двух подписок

Эталонный клиент держит **два** параллельных соединения (`web/src/App.tsx`, `web/src/lib/appSseSubscriptions.ts`):

1. **Глобальное** — `all=true`, живёт всю сессию приложения. Ведёт список сессий, список машин, бейджи, тосты.
2. **Сессионное** — `sessionId=<открытая сессия>`, пересоздаётся при каждом переключении сессии. Ведёт открытый чат.

Доставка на стороне хаба (`SSEManager.shouldSend`):

| Тип события | Доставляется кому |
|---|---|
| `connection-changed` | самому соединению |
| `heartbeat` | каждому соединению |
| `toast` | каждому **видимому** соединению в пространстве имён, независимо от фильтра (без `id`, никогда не воспроизводится) |
| `message-received`, `scheduled-matured` | соединениям `all=true` + соединениям с совпадающим `sessionId` |
| `session-added` / `session-updated` / `session-removed` / `session-ended` / `messages-invalidated` / `messages-consumed` / `messages-indeterminate` / `messages-requeued` / `message-cancelled` | соединениям `all=true` + соединениям с совпадающим `sessionId` |
| `machine-updated`, `machine-agy-models-updated` | соединениям `all=true` + соединениям с совпадающим `machineId` |

**Глобальное соединение также должно обрабатывать события потока сообщений** (`message-received`, `messages-consumed`, `messages-indeterminate`, `messages-requeued`, `message-cancelled`, `scheduled-matured`): пока сессионное соединение недоступно (разрыв при переподключении) или сессия не открыта, глобальный канал — единственный живой, и он всё ещё должен поддерживать корректный учёт очереди/оптимистичных сообщений — помечать локальные сообщения потреблёнными, удалять отменённые строки и обновлять счётчики запланированных в списке сессий. Сессионное соединение дополнительно поглощает `message-received` в окно сообщений.

У двух соединений **нет отношения порядка друг с другом** — один и тот же патч `session-updated` может прийти по обоим, в любом порядке. Именно поэтому ниже существует гейт версионированного патча.

## Объединение SyncEvent (16 типов)

Схема: `SyncEventSchema` в `shared/src/schemas.ts` (дискриминируется по `type`). Все события, кроме `connection-changed`, несут `namespace?: string`. Игнорируйте неизвестные типы событий.

| `type` | Payload (помимо `type`, `namespace?`) | Обработка клиентом |
|---|---|---|
| `session-added` | `sessionId`, `data?: unknown` | Обрабатывайте точно как `session-updated` (эталонный клиент делит ветку): полный `Session` делает upsert; всё остальное откатывается к перезапросу списка сессий. |
| `session-updated` | `sessionId`, `data?: Session \| SessionPatch` | См. [Алгоритм версионированного патча](#алгоритм-версионированного-патча). |
| `session-removed` | `sessionId` | Удалить сессию из списка, удалить её кеш деталей, очистить её окно сообщений. |
| `message-received` | `sessionId`, `message: DecryptedMessage` | Поглотить в окно сообщений; продвинуть курсор хвоста (см. [pagination](./pagination.ru.md)). Также испускается для собственной отправки вызывающего (эхо localId). |
| `messages-invalidated` | `sessionId`; rewind может также включать `reason: 'rewind'` и `truncateFromLocalId` | История сообщений изменилась **структурно** (rewind, fork, импорт, clear). При rewind сохраните только известный префикс до границы клиента перед синхронизацией хвоста; при любой другой инвалидации отбросьте всё окно и выполните свежую синхронизацию хвоста. В глобальной области: перезапросить список сессий. |
| `scheduled-matured` | `sessionId` | Запланированное сообщение стало актуальным и передано агенту. Перезапросить индикаторы списка/очереди. |
| `session-ended` | `sessionId`, `reason?: 'completed'\|'terminated'\|'error'\|'handoff'\|'cleared'` | Сигнал жизненного цикла сессии (поток `session-updated` всё равно несёт изменение состояния). |
| `machine-updated` | `machineId`, `data?: Machine \| MachinePatch \| null` | Полный `Machine`: upsert (удалить при `active:false`). `null`: машина удалена. Патч `{active?, activeAt?, updatedAt?}`: `active:false` ⇒ удалить, иначе перезапросить машины. `data` отсутствует ⇒ перезапросить. |
| `machine-agy-models-updated` | `machineId` | Список `agy models` машины изменился при фоновой перепроверке. Перезапросите `GET /api/machines/:id/agy-models` для этой машины (отвечается из кеша машины; не запускает `agy` и не порождает дальнейших событий). Испускается, когда перепроверка меняет то, что ответил бы этот маршрут, — другой список или появившееся/исчезнувшее предупреждение о входе — но никогда для первого списка машины. |
| `toast` | `data: {title, body, sessionId, url}` | Показать как встроенный в приложение тост/баннер. Доставляется только видимым соединениям (см. [Видимость](#видимость)). |
| `messages-consumed` | `sessionId`, `localIds: string[]`, `invokedAt: number` | Агент потребил сообщения пользователя из очереди: проставить `invokedAt`, переключить статус на `sent`, убрать из панели очереди. |
| `messages-indeterminate` | `sessionId`, `localIds: string[]` | У нативной отправки/мутации очереди неизвестный результат. Оставьте строку невызванной, покажите явное разрешение Retry/Cancel и не воспроизводите её автоматически. Retry/Cancel общего движка могут оставаться недоступными, пока согласование не докажет результат. |
| `messages-requeued` | `sessionId`, `localIds: string[]` | Явный Retry восстановил доставку в обычную очередь. Очистите маркер неопределённости. |
| `message-cancelled` | `sessionId`, `messageId`, `localId?` | Сообщение очереди отменено: удалите строку (совпадение по `messageId` **или** `localId`). |
| `heartbeat` | `data?: {timestamp}` | Питает watchdog устаревания. Иных действий нет. **Не несёт `id`.** |
| `connection-changed` | `data?: {status, subscriptionId?, resume?: 'ok'\|'gap'}` | Рукопожатие; см. [Рукопожатие и возобновление](#рукопожатие-и-возобновление). Сохраните `subscriptionId` для отчётов о видимости. **Не несёт `id`.** |

## Алгоритм версионированного патча

Самая подверженная ошибкам часть протокола. `session-updated.data` — это либо **полный `Session`**, либо **`SessionPatch`** (`shared/src/schemas.ts`); эталонная реализация `applySessionDetailPatch` в `web/src/hooks/useSSE.ts`.

1. **Полная сессия** (валидируется по `SessionSchema` и `data.id === event.sessionId`): заменить кешированную сессию целиком.
2. **Патч** (валидируется по строгой `SessionPatchSchema` — неизвестные ключи приводят к сбою — и непустой): применять поле за полем, как ниже.
3. **Отсутствующий или неразбираемый `data`**: откатиться к перезапросу деталей и списка сессий по REST.

Применение патча, поле за полем:

- **Плоские поля** — `active`, `thinking`, `activeAt`, `model`, `modelReasoningEffort`, `effort`, `serviceTier`, `permissionMode`, `collaborationMode`, `copilotAgentMode`, `backgroundTaskCount`: присваивание «побеждает последняя запись», когда присутствует. `activeTurnStartedAt` появляется в патчах, но эталонная реализация намеренно никогда не применяет его из патча (`web/src/lib/sessionPatch.ts`) — берите его только из payload полной сессии; фикстуры `sse/` это фиксируют.
- **`updatedAt`** — макс-монотонно: `updatedAt = max(cached.updatedAt, patch.updatedAt)`. Устаревшее воспроизведение никогда не должно двигать часы назад.
- **Версионированные подпатчи** — `metadata`, `agentState`, `todos`, `teamState` приходят каждый как обёртка `{version: number, value: …}`. Применяйте `value` и сохраняйте `version` **только когда `version` строго больше кешированной отметки**:

  | Обёртка | Кешированная отметка на `Session` | Тип `value` |
  |---|---|---|
  | `metadata` | `metadataVersion` | `Metadata \| null` |
  | `agentState` | `agentStateVersion` | `AgentState \| null` |
  | `todos` | `todosUpdatedAt` (отсутствует = 0) | `TodoItem[]` |
  | `teamState` | `teamStateUpdatedAt` (отсутствует = 0) | `TeamState \| null` — `null` означает «команда удалена»: очистить её |

  Строго больше, потому что у двух соединений SSE **нет общего порядка** — одна и та же версия может прийти дважды, а более старая версия — после более новой. Применение устаревшего `agentState` воскресило бы разрешённые запросы разрешений; устаревший `metadata` откатил бы состояние resume/session-id. (Веб-путь *списка* сессий терпит `>=`, потому что повторный вывод его сводки из равной версии идемпотентен; для нативного клиента с одним кешем правило — строгое `>`.)
- **Никогда не разворачивайте обёртку целиком.** `session.metadata` должен стать `wrapper.value` — присваивание самого `{version, value}` в сессию это классическая ошибка портирования.
- **`scratchlistUpdatedAt`** — просто триггер перезапроса: патч не несёт записей; его присутствие означает «перезапросить `GET /api/sessions/:id/scratchlist`». Больше применять нечего.

### Шум keep-alive

Keep-alive CLI заставляет хаб пере-транслировать патч примерно **каждые 10 с на активную сессию**, в котором обычно движется только `activeAt`. Рекомендация (веб: `isRenderIrrelevantSessionPatch`): считайте патч нерелевантным для отрисовки, когда единственное эффективное изменение — дельта `activeAt` **< 60 с** (метки относительного времени меняются только на границах минут); путь списка сессий полностью игнорирует `activeAt`. Применяйте данные, если хотите, но не перерисовывайте и не пересортируйте шесть раз в минуту из-за этого.

Эталонная сортировка списка (веб): `globalPinned` > `pinned` > `active` > `pendingRequestsCount` (среди активных) > `updatedAt` по убыванию.

### `active` — это живость транспорта, а не здоровье агента

По `Session` путешествуют два разных сигнала, и клиенты регулярно их путают (tiann/hapi#1820):

| Сигнал | Означает | Обновляется |
|---|---|---|
| `active` / `activeAt` | сокет CLI подключён и доступен | keep-alive `session-alive`, примерно каждые 2 с |
| `metadata.lifecycleState` | что на самом деле делает агент за этим сокетом | только переходами жизненного цикла |

Сессия может держать `active: true` бесконечно на одних keep-alive, без сообщений и размышлений, днями. Это живой сокет перед простаивающим агентом, а не работающая сессия.

`metadata.lifecycleState` — сигнал здоровья:

- `running` — живая рабочая сессия (проставляется CLI при старте сессии)
- `idle` — хаб не видел ничего, кроме keep-alive, в течение `HAPI_SESSION_IDLE_TIMEOUT_MS` (по умолчанию 12 ч). Обратимо и неразрушающе: `active` остаётся `true`, и следующее сообщение, запрос в очереди или фоновая задача возвращает его в `running` в пределах одного тика хаба
- `archived` — сессия закрыта

Правила клиента:

- Считайте и `running`, и `idle` как «CLI всё ещё владеет этой сессией». Сравнение с литералом `'running'` заставляет `idle`-сессию читаться как мёртвая строка.
- Показывайте `idle` отлично от `active`-и-недавно-работающей, чтобы оператор мог отличить занятый парк от груды keep-alive-зомби (веб: корзина `idle` в `SessionList`).
- Сессии, которым положено тихо простаивать бесконечно, могут задать `metadata.idleReconcileExempt: true`, чтобы полностью отказаться от согласования.

## Видимость

`POST /api/visibility` с телом `{"subscriptionId": "<from connection-changed>", "visibility": "visible" | "hidden"}` → `{"ok": true}`. Ошибки: `400` неверное тело, `404` неизвестный `subscriptionId` (или несовпадение пространства имён), `503` хаб не готов. У каждого нового соединения **новый** `subscriptionId` — сообщайте заново после каждого переподключения (веб-эталон сообщает о обоих своих соединениях при каждом переходе передний план/фон и повторяет неудачный отчёт через 2 с).

Семантика (`hub/src/visibility/visibilityTracker.ts`, `hub/src/push/pushNotificationChannel.ts`): нативная доставка Android/iOS не зависит от видимости веба. Когда нативный провайдер принимает уведомление хотя бы для одного устройства, хаб пропускает дубликат Web Push/тоста для этой отправки. Иначе, если **любое** соединение в пространстве имён видимо, хаб сначала отправляет **кадры SSE `toast` видимым соединениям**. Web Push — запасной вариант, когда ни одно соединение не видимо или доставка тостов достигает нуля соединений. Принятие провайдером — не квитанция о доставке на аппарат — см. [контракт нативного компаньона](../native-companion-contract.ru.md).

Нативное правило: сообщайте `visible` при выходе на передний план и `hidden` при уходе в фон, каждый раз. Устаревший отчёт `visible` может увести запасной Web Push пространства имён в невидимые кадры тостов; он не отключает нативный push. Нативное приложение отдельно подавляет своё локальное уведомление, когда соответствующий чат уже открыт на переднем плане.

## Gzip

Ответы SSE сжимаются gzip, когда `Accept-Encoding` это позволяет (`hub/src/web/sseCompression.ts`): хаб управляет zlib напрямую и выполняет **синхронный сброс после каждого чанка**, поэтому события приходят немедленно, несмотря на сжатие (~75 % коэффициент на реальном трафике). Согласование учитывает q-значения (`gzip;q=0` отказывает, `*` учитывается); ответ несёт `Content-Encoding: gzip` без `Content-Length`.

Нативные клиенты должны убедиться, что их HTTP-стек **распаковывает поток инкрементально** (кадры видны на каждый сброс, а не буферизуются до EOF). Если нет — или если он автоматически распаковывает только когда сам добавил `Accept-Encoding`, — отправьте `Accept-Encoding: identity` и возьмите несжатый поток.
