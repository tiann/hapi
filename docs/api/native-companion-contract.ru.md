# Контракт API нативного компаньона (телефон + Wear + iOS)

**Аудитория:** разработчики нативных приложений-компаньонов (Android-телефон + Wear OS через FCM, iOS через APNs), сопрягаемых с хабом hapi.

**Аутентификация:** обменяйте `code` сопряжения / токен доступа CLI через `POST /api/auth`:
`{ "accessToken": "<code>" }`. Используйте возвращённый JWT как `Authorization: Bearer <token>`
для регистрации устройства и действий с сессиями. `POST /api/bind` — только для привязки
Telegram Mini App (требует Telegram `initData`).

## Область

Компаньон, реализующий этот контракт, — это **нативный клиент того же хаба, с которым говорит PWA**, показывающий уведомления и действия «ответить / одобрить» на телефоне или носимом устройстве. Хаб может работать на машине разработчика оператора или на отдельном хосте; агенты выполняются на его машинах CLI/Runner.

Эта страница описывает фоновый push. Приложения iOS и Android из репозитория
также предоставляют интерактивные сессии и чат; см. [руководство по нативным приложениям](../guide/native-apps.md) (англ.)
и [контракт клиента](./client-contract/index.ru.md). Хаб сохраняет поддержку прямого FCM
для регистраций `wear`; приложение Wear OS в репозиторий не входит.

## Регистрация нативного устройства

### Регистрация

`POST /api/devices/register`

```json
{
  "token": "<fcm-registration-token>",
  "platform": "phone",
  "deviceId": "<stable-install-id>",
  "pushKey": "<base64 of 32 device-generated random bytes>"
}
```

`platform`: `"phone"` | `"wear"` | `"ios"`.

`pushKey`: обязателен для iOS и для доставки через Android-реле. Новые Android-клиенты
телефона всегда его передают. Регистрации phone без него остаются действительными для
прямого FCM; переданные ключи phone должны декодироваться ровно в 32 байта. Wear игнорирует
это поле. Хаб канонизирует и сохраняет ключи phone/iOS в существующем реестре; изменения
схемы или версии базы данных не требуется.

`deviceId`: любая строка из 1–128 символов, выбранная клиентом (не обязана быть UUID). Должна быть стабильной между повторными регистрациями одной установки.

**Ответ:** `{ "ok": true }`

Upsert по `(namespace, deviceId, platform)` — то же устройство при повторной регистрации заменяет свой push-токен.

### Отмена регистрации

`DELETE /api/devices/register`

```json
{
  "token": "<fcm-registration-token>"
}
```

## Исходящий push (хаб → устройство)

Хаб отправляет нативные уведомления независимо от видимости PWA.
Android использует прямой FCM или зашифрованное реле в зависимости от конфигурации хаба;
iOS использует APNs или зашифрованное реле. Успешная отправка хотя бы на одно нативное
устройство устанавливает гейт на отправку, подавляющий Web Push для этого события и
пространства имён. Отсутствующие регистрации, отсутствующие ключи шифрования реле и
неудачные отправки не подавляют запасной вариант. Принятие провайдером — не квитанция
о доставке на аппарат.

### Payload данных (все платформы)

| Ключ | Пример | Назначение |
|------|--------|-----------|
| `type` | `ready` | `ready`, `permission-request`, `input-request`, `task-notification` |
| `sessionId` | uuid | Целевая сессия |
| `sessionName` | string | Отображаемое имя (`agent - project`) |
| `url` | `/sessions/{id}` | Путь диплинка |
| `requestId` | request-id | Ключ карты ожидающих запросов: approve/deny для разрешения, только корреляция для input |
| `title` | string | Заголовок уведомления |
| `body` | string | Тело уведомления |
| `severity` | `info` | `info` (ready/input), `warning` (permission), `success` / `error` (task) |
| `contractVersion` | `1` | Присутствует в каждом сообщении; см. [Версионирование](#версионирование) |
| `notifySummary` | JSON string | Только в `ready`: разобранная строка `AGENT_NOTIFY_SUMMARY` из текста агента, когда есть |

Прямой FCM — data-only. Сообщения Android-реле содержат зашифрованную обёртку
ниже; после расшифровки тот же контракт данных управляет отрисовкой и действиями.

### Вопросы (`input-request`)

Вопросы пользователя — не одобрения инструментов. Хаб испускает `input-request` для
`request_user_input`, `AskUserQuestion`, `ask_user_question` и
`CursorAskQuestion` (включая известную обёртку `functions.`). Одобрение плана
(`ExitPlanMode`), асинхронные инструменты и произвольные суффиксы имён MCP не
классифицируются как вопросы.

Заголовок — `<agent> needs your input`. Тело начинается с первого читаемого
вопроса (с откатом к его `header`), затем `+N more question(s)` для оставшихся
читаемых вопросов, затем имя сессии. Пробелы схлопываются внутри каждой
строки. Тело ограничено 280 кодовыми точками Unicode, из них не более 80 на
имя сессии, с усечением только на границах графем. Никакие варианты, предзаполненные
ответы, id протокола или сырые аргументы инструментов не попадают в превью. Искажённый
ввод откатывается к `Open the session to view and answer the question.`

Клиенты отрисовывают этот тип **только с открытием по нажатию**: никаких Allow/Deny и
никакого обычного ответа на сообщение, даже когда `requestId` присутствует. Пользователи
отвечают через существующую форму вопроса сессии. Android направляет его в отдельный
канал `input_requests` важности HIGH; iOS не назначает категорию действия. Apple Watch
сейчас зеркалит превью, а ответ оставлен телефону (приложения watchOS или встроенного
потока ответа нет). Идентичность `input-request-<sessionId>` отделяет вопросы от
уведомлений о разрешениях.

Это аддитивный тип в версии контракта 1. Существующая обработка неизвестных типов
уже отрисовывает заголовок/тело без специфичных для типа действий. Хаб сохраняет
текущий выбор первого ожидающего и поведение debounce; это не меняет
планирование запросов, API ответов или отзыв уведомлений.

### Действия клиента (нативные — не хаб)

| Действие пользователя | API хаба |
|-----------------------|----------|
| Отправить текст | `POST /api/sessions/:id/messages` `{ "text": "...", "localId": "..." }` |
| Разрешить | `POST /api/sessions/:id/permissions/:requestId/approve` |
| Отклонить | `POST /api/sessions/:id/permissions/:requestId/deny` |

`localId` необязателен в теле отправки сообщения — непрозрачный сгенерированный клиентом id для согласования локально показанного сообщения с отражённым сервером.

REST-эндпоинт отправки проставляет `sentFrom: 'webapp'` на стороне сервера как для нативных,
так и для веб-отправок; клиенты не передают поле `sentFrom`. См.
[Messages](./client-contract/rest.ru.md#сообщения).

## Android-реле

Официальное Android-приложение включает клиентскую конфигурацию Firebase сопровождающего.
Текущий хаб без приватных учётных данных Firebase отправляет на
`https://push.hapi.run`; пользователям нужно лишь сопрячься и разрешить уведомления. Сервисы
Google Play и сетевой доступ к FCM всё ещё требуются. Подготовка проекта Firebase во время
выполнения и доставка через Wear-реле выходят за рамки этой версии.

Приложение сохраняет один `deviceId` и случайный `pushKey` в отдельном зашифрованном
Keystore файле настроек, исключённом из резервного копирования и переноса устройства.
Регистрация происходит только после успешного сохранения. Первое обновление со старого
DataStore ID регистрирует новую идентичность; дедупликация токенов удаляет старую строку.
Ротация токена сохраняет ключ и ID. Регистрация веером идёт во все сопряжённые хабы при
запуске, сопряжении, ротации токена и повторах воркера.

Хаб использует тот же [зашифрованный конверт](#зашифрованный-конверт), что и iOS.
`POST {relayUrl}/v1/push` несёт:

```json
{"platform":"android","token":"<opaque FCM token>","envelope":"<base64>","priority":10}
```

FCM отправляет только строковые значения `data: {"hapi_v":"1","hapi_e":"<envelope>"}`,
с приоритетом Android `HIGH` (`NORMAL` для приоритета реле `5`) и настроенным
`restricted_package_name`. Ни `notification`, ни `collapse_key` не отправляются.
Существующий TTL FCM по умолчанию сохраняется. Android расшифровывает локально, затем
передаёт поля v1 существующему рендереру, воркерам действий и логике
открытия/подавления-когда-открыто сессии. Присутствующий зашифрованный маркер с
неизвестной версией, отсутствующим ключом, искажённым JSON или неудачной аутентификацией
отбрасывается и никогда не трактуется как открытый текст. Развёрнутые данные прямого FCM
по-прежнему поддерживаются.

Зашифрованный конверт ограничен 3200 байтами Base64. При необходимости хаб удаляет
`notifySummary`, затем откатывается к минимальному уведомлению `HAPI / New activity`,
сохраняя тип, id сессии, id запроса и версию контракта. Он никогда не усекает шифротекст
или id действий. Если даже минимум превышает лимит, отправка не удаётся, а регистрация
сохраняется.

`410 unregistered` реле удаляет токен. `413`, `429`, `501`, ошибки аутентификации/сети
и несовпадение проекта Firebase сохраняют его. Реле не ставит отправки в очередь и не
повторяет их. Реле и Google видят токены и метаданные доставки, но не могут прочитать
содержимое уведомления; приватный путь прямого FCM сохраняет свой существующий
незашифрованный payload.

## iOS (APNs)

iOS — полноценный нативный компаньон с **тем же контрактом уведомлений**, что и Android, доставляемым через APNs вместо FCM. Как и доставка через Android-реле, payload **защищён сквозным шифрованием**: ни Apple, ни необязательное push-реле hapi не могут прочитать содержимое уведомления (PUSH SPEC v1).

### Регистрация

`POST /api/devices/register`

```json
{
  "token": "<hex-apns-device-token>",
  "platform": "ios",
  "deviceId": "<stable-install-id>",
  "pushKey": "<base64 of 32 device-generated random bytes>"
}
```

- `token`: hex-кодированный токен устройства APNs из `didRegisterForRemoteNotificationsWithDeviceToken`.
- `pushKey`: **обязателен для `ios`** — 32 случайных байта, сгенерированных на устройстве
  (например, `SecRandomCopyBytes`), в base64. Это ключ сквозного шифрования на устройство;
  хаб проверяет, что он декодируется ровно в 32 байта, и иначе отклоняет регистрацию.
  Храните его в Keychain (общий с Notification Service Extension через группу доступа
  Keychain). Обе цели iOS объявляют `$(AppIdentifierPrefix)run.hapi.companion.push` в
  `keychain-access-groups`; контейнер App Group для этого ключа не используется.
  Ротируйте его повторной регистрацией.
- Upsert по `(namespace, deviceId, platform)`, как в Android. Отмена регистрации —
  тот же `DELETE /api/devices/register` `{ "token": ... }`.

### Зашифрованный конверт

Открытый текст — это точный JSON [payload данных](#payload-данных-все-платформы)
(`type`, `sessionId`, `sessionName?`, `url?`, `title`, `body`, `severity?`,
`contractVersion`, `requestId?`, `notifySummary?`), сериализованный как
**канонический JSON** — рекурсивно отсортированные ключи объектов, без пробелов,
отсутствующие необязательные поля опущены.

Шифрование: **AES-256-GCM** с `pushKey` устройства:

```
envelope = base64( nonce(12 random bytes) || ciphertext || tag(16 bytes) )
AAD      = ASCII "hapi-push-v1"
```

Золотой тестовый вектор (ключ `0x00..0x1f`, nonce `0x00..0x0b`):
[`shared/fixtures/push/envelope-v1.json`](https://github.com/tiann/hapi/blob/main/shared/fixtures/push/envelope-v1.json) —
реализация iOS должна воспроизвести его байт в байт.

### Запрос APNs (что получает устройство)

```json
{
  "aps": {
    "mutable-content": 1,
    "alert": { "title": "HAPI", "body": "New activity" },
    "sound": "default"
  },
  "hapi": { "v": 1, "e": "<envelope>" }
}
```

Общий алерт `"HAPI / New activity"` — запасной вариант без расшифровки. **Notification
Service Extension** приложения (вызывается через `mutable-content: 1`) расшифровывает
`hapi.e` ключом `pushKey` из Keychain и заменяет заголовок/тело реальным содержимым;
`hapi.v` — версия конверта (сейчас `1`).

Заголовки доставки: `apns-push-type: alert`, `apns-priority: 10`,
`apns-expiration: 0`, `apns-collapse-id: "<type>-<sessionId>"` (усечён до
64 байт) — чтобы более новые уведомления для той же сессии/типа заменяли старые.

### Транспорты: самостоятельный хостинг (прямой APNs) против официального реле

Хаб выбирает один из двух транспортов через `HAPI_IOS_PUSH` (или поле
`iosPushMode` в `~/.hapi/settings.json` — у каждой переменной ниже есть эквивалент в
settings.json, см. [Окружение](#окружение-оператор-хаба)):

| Режим | Кто говорит с Apple | Требования |
|-------|---------------------|------------|
| `relay` (по умолчанию) | push-реле hapi (`https://push.hapi.run`), которое хранит учётные данные APNs для официального приложения | нет |
| `apns` | сам хаб, по HTTP/2 с провайдерским JWT ES256 | аккаунт разработчика Apple: ключ аутентификации `.p8`, key id, team id, bundle id |
| `off` | никто | — |

```bash
# default: official relay (zero setup)
HAPI_IOS_PUSH=relay
HAPI_PUSH_RELAY_URL=https://push.hapi.run   # override for a self-hosted relay

# self-host: direct APNs, no relay involved
HAPI_IOS_PUSH=apns
APNS_KEY_P8_PATH=/path/to/AuthKey_XXXXXXXXXX.p8
APNS_KEY_ID=XXXXXXXXXX
APNS_TEAM_ID=YYYYYYYYYY
APNS_BUNDLE_ID=your.ios.bundle.id
APNS_ENV=production   # or sandbox (Xcode/dev builds)
```

Учётные данные прямого APNs должны совпадать с аккаунтом разработчика подписи приложения и
bundle ID, а `APNS_ENV` — с окружением его токена устройства. Смена аккаунта разработчика
или bundle ID для самостоятельной сборки требует соответствующей конфигурации провайдера;
учётные данные официального реле не могут доставлять в произвольное самостоятельно
подписанное приложение. Самостоятельное реле также должно использовать совпадающие учётные
данные. См. [инструкции по сборке iOS](https://github.com/tiann/hapi/blob/main/ios/README.md#push-notifications).

Протокол реле (для самостоятельно размещённых реле): `POST {relayUrl}/v1/push` с
`{"platform":"ios","token":"<hex>","envelope":"<base64>","collapseId":"...","priority":10}`;
ответы `200 {ok:true}`, `410 {ok:false,"code":"unregistered"}` (хаб удаляет строку
устройства), `413` / `429` трактуются как временные.

Обработка мёртвых токенов повторяет FCM: APNs `410 Unregistered` или
`400 BadDeviceToken` (и `410` реле) отменяют регистрацию строки устройства; временные
ошибки (аутентификация, throttle, 5xx, сеть) — никогда.

### Конфиденциальность

Открытый текст уведомления существует только на хабе и на сопряжённом устройстве.
Push-инфраструктура Apple и реле (официальное или самостоятельно размещённое) видят
**только шифротекст плюс метаданные маршрутизации** (токен APNs, collapse id, время,
размер). `pushKey` никогда не покидает устройство, кроме как к собственному хабу оператора
через аутентифицированный вызов регистрации. Операторы, предпочитающие нулевое участие
третьих сторон сверх Apple, запускают `HAPI_IOS_PUSH=apns`.

Как и канал FCM, iOS-push срабатывает безусловно для зарегистрированных устройств и
подавляет запасной Web Push для пространства имён, когда отправка успешна (одно уведомление
ОС, а не два).

## Окружение (оператор хаба)

| `HAPI_ANDROID_PUSH` | Поведение |
|---|---|
| `auto` (по умолчанию) | Настроен `FCM_SERVICE_ACCOUNT_PATH`: прямой FCM; иначе официальное реле |
| `relay` | Принудительно реле, игнорируя приватные учётные данные Firebase |
| `fcm` | Требовать приватные учётные данные Firebase, прямая доставка phone/Wear |
| `off` | Отключить push Android/Wear |

```bash
# Default: no Firebase configuration needed for official Android apps.
HAPI_ANDROID_PUSH=auto
HAPI_PUSH_RELAY_URL=https://push.hapi.run

# Private-project builds must match the service account's Firebase project.
HAPI_ANDROID_PUSH=fcm
FCM_SERVICE_ACCOUNT_PATH=/path/to/service-account.json
```

ID проекта Firebase берётся из JSON сервисного аккаунта. Отсутствующие/сломанные явные
учётные данные или неизвестный режим Android отключают канал с диагностикой; они никогда
молча не переключают приватные токены на официальный проект. Один хаб выбирает один
транспорт/проект Android; смешивание сборок из разных проектов Firebase не поддерживается.
Выбор транспорта iOS (`HAPI_IOS_PUSH`, `APNS_*`) независим. Push-реле не зависит от
того, включён ли сетевой туннель хаба (`--relay`).

Конфигурация push следует общехабному правилу (env > `settings.json` >
по умолчанию; значение env сохраняется в `~/.hapi/settings.json` при первом
обнаружении, поэтому переменную нужно передать лишь один раз). Ключи settings.json:
`androidPushMode`, `fcmServiceAccountPath`, `iosPushMode`, `iosPushRelayUrl`, `apnsKeyP8Path`,
`apnsKeyId`, `apnsTeamId`, `apnsBundleId`, `apnsEnv`. Историческая настройка
`iosPushRelayUrl` задаёт общий URL для обеих платформ. Значения путей могут использовать `~`.

Канал нативного push **включается по желанию**: операторы, не запускающие приложение-
компаньон, не видят изменений в поведении. Когда хотя бы одна нативная отправка успешна для
уведомления, Web Push подавляет это уведомление для пространства имён, чтобы избежать
двойного уведомления (одно в нативном приложении, одно от service worker PWA). Операторы
только с PWA не затронуты.

## Версионирование

Версия контракта **1**. Ломающие изменения требуют `data.contractVersion` в payload FCM и обновления документации.
