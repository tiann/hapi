# Общие сессии Codex

Codex **0.154.0 и новее**: официальный терминальный UI и веб/нативные
клиенты HAPI используют один app-server. Нет переключения владения «локально/удалённо». Обе стороны могут отправлять
сообщения, одобрять инструменты и отвечать на `request_user_input`.

```bash
hapi codex                          # запустить выполнение, принадлежащее этому терминалу
hapi resume <hapi-session-id>        # подключиться к живому выполнению на этой машине
hapi codex resume <native-thread-id> # холодное возобновление; отклоняет другого живого владельца
hapi codex resume --last             # последний нативный поток в текущем каталоге
```

Выполнение использует окружение, аутентификацию и `CODEX_HOME` запуска.
Независимые запуски получают независимые app-server'ы, а не глобальный сервис
агента. Повторное подключение использует **тот же исполняемый файл**, что и работающий app-server, даже если PATH
с тех пор изменился. Когда один раннер уже запущен, требуется совместимый раннер.
Обновляйте CLI, Runner и Hub вместе: Hub должен сохранять общий ожидающий ввод
при завершении выполнения, а не применять устаревшую очистку очереди по окончании сессии.

## Жизненный цикл

- **Выполнение, созданное из терминала**: исходный терминал владеет его временем жизни.
  `/exit` или закрытие этого терминала останавливает его app-server. Все корни в этом
  выполнении становятся **неактивными, а не архивными**; подключённые терминалы отключаются.
- **Выполнение, созданное/возобновлённое из веба**: существующий Runner запускает обычную
  обёртку HAPI. Основной терминал не требуется.
- **Дополнительные терминалы**: `hapi resume <id>` подключается к существующему движку.
  Выход из подключённого терминала только отключает; он никогда не забирает владение временем жизни.
- **Веб после остановки выполнения**: существующий поток resume-on-send просит
  онлайн-Runner восстановить ту же HAPI-сессию/нативный поток, затем доставляет
  сообщение. Runner должен иметь доступ к тому же нативному хранилищу (`CODEX_HOME`)
  и учётным данным. Без нового фонового демона Codex или пути handoff, и без попытки
  сериализовать/воссоздать произвольное окружение терминала.
- **Остановка**: прерывает текущий ход; поток и нативная очередь сохраняются.
- **Завершение сессии**: архивирует этот корень и его потомков. Соседние корни продолжают работать.
- `/new`, `/clear`: создают новый корень/HAPI-сессию. Другие клиенты остаются на старом корне.
- Нативные `/resume` и `/fork`: привязывают выбранный/новый корень перед тем, как показать
  ответ о жизненном цикле. Одна HAPI-идентичность никогда не перенаправляется на другой поток.
- Веб/мобильные `/new` и `/clear`: только инициирующее представление следует за возвращённым
  идентификатором сессии. Нет глобального редиректа на «заменённую» сессию.
- Переход к потоку, принадлежащему другому живому выполнению, отклоняется с
  инструкцией `hapi resume <id>`. Без дублирующего живого движка и автоматического роуминга.

Последний заархивированный корень останавливает свой app-server. В остальном время жизни следует
за исходным терминалом или обёрткой, запущенной Runner'ом, **а не за количеством фронтендов**.
`/new` и fork не переносят владение: когда исходный терминал выходит,
его соседние корни тоже становятся неактивными. Каждый позже может быть возобновлён независимо.
Другие выполнения не затрагиваются. Прерванная/незавершённая работа не проигрывается
вслепую; resume восстанавливает долговечную историю, а не память старого процесса.

## Сообщения и вопросы

Завершённые предложения режима Plan остаются видимыми в чате, в том числе после действий
в терминале, обновления и resume. Текущее предложение предлагает в вебе **Implement plan** и
**Continue planning**. Implement переключает нативный поток в Default
и ставит в очередь `Implement the plan.`; Continue фокусирует редактор в режиме Plan.
Это действия клиента, а не одобрения инструментов. Выбор Codex «остаться в Plan
mode», доступный только в терминале, не транслирует решение другим клиентам. Новый нативный
ход или смена режима убирает устаревшие веб-элементы управления, сохраняя план.
Codex 0.154 может оставить своё локальное меню подтверждения открытым после веб-выполнения;
нажмите **Esc** перед вводом следующей команды терминала.

Обычные сообщения HAPI попадают в **нативную очередь Codex**. Конкурирующего
«опустошителя» очереди HAPI нет. Настройки читаются при выполнении отправки, а не
замораживаются при постановке в очередь. Явный **Steer** нацелен на текущий наблюдаемый ход;
устаревший идентификатор хода отклоняется, а не перенаправляется на следующий ход.

Текст нативной ожидающей очереди зеркалируется в HAPI. Нативные правки и подтверждённые
удаления обновляют его. Потеря элемента очереди при восстановлении транспорта не является
доказательством, что он был отменён или выполнен.

Codex арбитрирует ответы терминала и веба. Отправленный из веба ответ — только
кандидат. Нативный `serverRequest/resolved` закрывает запрос с нейтральным статусом
**Resolved in Codex**; HAPI не выдумывает победителя и его ответ.
Отключение убирает старые элементы управления; переподключение воспроизводит нативные ожидающие запросы.
Отмена вопроса прерывает его нативный ход, а не отправляет пустой
сфабрикованный ответ. Неизвестные типы запросов от боковых клиентов остаются только в терминале.

У каждого корня свой HAPI-сокет, MCP-мост и оболочка `HAPI_SESSION_ID`.
Трейсы/разрешения дочерних агентов атрибутируются по нативному происхождению, а не просто
по факту получения на том же соединении app-server'а.

## Восстановление и локальные данные

- Сбой хаба: существующие нативные потоки продолжаются. Переподключение сверяет историю,
  очередь и ожидающее состояние по стабильным идентификаторам.
- Перезапуск Runner'а: используется существующее отслеживание/восстановление процессов Runner'а. Живое подключение
  использует записи приватных эндпоинтов напрямую; без лишнего цикла сканирования/усыновления. Неизвестные
  вебхуки общих корней — не повод убивать соседнее выполнение.
- Обычный выход выполнения: прекратить новые отправки, удалить нативный ожидающий ввод
  там, где Codex подтверждает, что он не выполнен, и сохранить его для обычного воспроизведения Hub'ом
  при resume (включая нативные правки и ожидающие загрузки файлов). Убрать ожидающие
  элементы управления разрешениями/вопросами. Остановить движок до публикации неактивности.
- Падение обёртки/app-server'а: нет автоматического воспроизведения принятых или неопределённых записей.
  Долговечный журнал очереди на сессию фиксирует неизвестные исходы до отправки.
- Холодное возобновление проверяет поколения процесса обёртки **и** app-server'а. Живой
  «сирота» или непроверяемое поколение блокирует восстановление. Осмотрите и явно
  остановите этого «сироту» перед возобновлением; никогда не удаляйте просто запись о владении.
- Неподтверждённые операции жизненного цикла помещаются в карантин и логируются; слепое повторение
  `/new`, fork или send может создать дублирующуюся работу.
- Активные устаревшие локальные/удалённые сессии не мигрируются «на горячую». Остановите их явно
  перед холодным возобновлением с новым CLI.

Приватные файлы: `$HAPI_HOME/codex-runtimes` (записи живых эндпоинтов/владения, журналы
очередей), `$CODEX_HOME/hapi-runtime-owners` (владение на уровне хранилища, включая
разные HAPI home). Unix-сокеты живут в короткоживущем приватном временном
каталоге. Windows использует loopback-WebSocket'ы с bearer-аутентификацией. Эндпоинты/токены
app-server'а никогда не попадают в метаданные HAPI-сессии или SSE.

## Текущие ограничения

- Холодное возобновление принимает только корневые потоки. Чтобы вернуться к дочернему агенту, возобновите
  его родительскую HAPI-сессию; HAPI не запускает дочернее выполнение независимо.
- Устаревшая политика автоодобрения `safe-yolo` HAPI — не нативный режим Codex;
  общие сессии отклоняют её, а не ослабляют или искажают отчёт о ней.
  Используйте `default`, `read-only`, `yolo` или нативный `--approve-for-me`.
- Новые корни `/new`/fork, созданные из веба, сохраняют стандартные нативные ограничения песочницы.
  Именованные профили разрешений и внешние песочницы должны создаваться в
  нативном TUI; HAPI никогда не преобразует их молча в workspace-write.
- `--profile` / `-p`: отклоняется. Автономный app-server 0.154 не может выбрать
  нативный загрузчик profile-v2; сведение его в `-c` меняет приоритет
  конфигурации. Используйте отдельный `CODEX_HOME` или явные переопределения `-c`.
- Нативный in-place rewind/rollback и веб-Rewind недоступны для параллельных
  сессий: нативная мутация плюс обрезка транскрипта хаба требует барьера
  фиксации между всеми отправителями. Используйте **Fork at message** вместо этого. Обрезки внутри
  направленного (steered) хода отклоняются; выберите его первое пользовательское сообщение.
- `--worktree` и неподдерживаемые флаги запуска завершаются явной ошибкой; создайте/выберите
  рабочий каталог перед запуском. `--oss` требует явный
  `--local-provider`. Обычные меню resume используют `hapi resume` или подключённый TUI.
- На неизвестные формы запросов MCP HAPI не отвечает. Ошибка бокового клиента
  в ответе может поглотить нативный колбэк и закрыть корректный запрос TUI.
- Нативные запросы только с изображениями сохраняют плейсхолдеры изображений в HAPI; они не
  загружают локальное изображение терминала как превью веб-вложения.
- macOS-тесты real-binary/full-stack используют изолированные home и локальный мок-
  эндпоинт Responses; подписка Claude или платные вызовы модели не требуются.
  Аутентификация транспорта Windows покрыта юнит-тестами; нативное выполнение Windows
  всё ещё требует валидации на платформе.

## Тесты

```bash
bun typecheck
bun run test
HAPI_RUN_SHARED_CODEX_TESTS=1 bun run --cwd cli test -- \
  src/codex/shared/runtime.integration.test.ts \
  src/codex/shared/frontend.integration.test.ts
```

При включённом глобальном Web Storage Node 26 существующая веб-тестовая настройка может
конфликтовать с типом `StorageEvent` jsdom. В таком окружении запускайте набор с
`NODE_OPTIONS=--no-experimental-webstorage bun run test`.

Опциональные тесты требуют установленный официальный бинарь Codex. Полнофункциональный
терминальный тест также использует поддержку PTY из стандартной библиотеки Python 3 (только POSIX).
Он прогоняет реальные HAPI CLI/Runner, hub REST/Socket.IO, MCP, app-server и нативный TUI,
а не поддельный исполняемый файл Codex. Покрытие включает ответы с клавиатуры/из веба, изоляцию соседних
вопросов, редактирование/удаление нативной очереди, fork, выход основного терминала,
подключение/отключение вторичного терминала, возобновление Web→Runner с той же HAPI/нативной
идентичностью и безопасное восстановление ожидающих сообщений.
