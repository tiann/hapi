# Release Notes Authoring

The in-app release history is maintained in `web/src/lib/releaseNotes.ts`. It
is bundled with the Web app so users can read it offline. Keep the catalog
newest-first. Add the target version before preparing the release; the release
script checks that the entry leads the catalog before it bumps versions,
commits, tags, and pushes.

## Release sequencing

Release authors should prepare and merge the release-note entry before running
the release script:

1. Add the target version, date, bilingual summary, and grouped changes.
2. Run the focused release-note tests and review the generated copy.
3. Merge the release-note change into `main`.
4. Run the release script. It verifies that the target version leads the
   catalog, updates the version files and lockfile, and commits, tags, and
   pushes the release.
5. Let the tag-triggered Release workflow build the binaries, publish to npm,
   and create the GitHub Release.

Do not wait until after the tag is created to add the entry: that would publish
a build whose About page still ends at the previous version.

During preparation, the catalog test only requires the current
`__APP_VERSION__` to exist somewhere in the history. This allows the next
release entry to be prepared at the top of the list while the repository still
has the previous version in `shared/src/buildInfo.ts`. At release time,
`release-all.ts` performs the stricter check that the requested version is the
first catalog entry before it prepares the release commit and tag.

## Source of truth

Start with the commits and code changed in the release tag range. Maintainers
sometimes push directly to `main`, so a change may have no pull request and a
GitHub Release body may contain only a **Full Changelog** compare link. That
means the written notes are missing; it does not mean the release had no
changes.

1. Use the compare base linked from the GitHub Release when it is present,
   otherwise use the previous release tag.
2. Review `git log --no-merges <base>..<target>` and the relevant `git diff`.
   Include direct commits even when they have no PR.
3. Use pull requests, release bodies, tests, and the implementation itself as
   supporting evidence. Do not infer behavior from a title alone.
4. Only describe a release as version-only after confirming that the diff
   contains just version metadata. For tests, CI, refactors, or packaging
   changes, name the concrete work instead of writing a generic maintenance
   placeholder.

Keep the release URL generated by `releaseNote()` so the version remains the
direct link to the complete GitHub release page.

## Format and ordering

Every entry must contain:

- the release date in `YYYY-MM-DD` (UTC);
- one English summary and one Simplified Chinese summary;
- groups that merge changes from the same product area;
- a `feature` change for a user-visible addition;
- a `fix` change for a bug fix, compatibility correction, or reliability fix;
- a `note` change for verified version-only, test, CI, documentation, or
  internal maintenance work that has no direct user-facing behavior change.

Write the most important user-facing changes first. Put feature groups and
feature bullets before fixes when both are present. Do not create groups named
`CLI`, `Web`, `Agent`, or similar merely to repeat a technical scope; name the
product area or user outcome instead. Mention the affected Agent or surface in
the sentence when it helps the reader understand the impact.

Each bullet should describe one concrete outcome. Prefer:

> Added Pi model-aware thinking controls so unavailable levels are hidden and
> stale selections reset safely.

Avoid:

> Updated Pi code and fixed several issues.

The English and Chinese text must carry the same meaning. Preserve product
names, commands, API names, environment variables, and code formatting. Do
not include author names, PR numbers, internal implementation trivia, or a
second “full release notes” link in the in-app copy—the version itself is the
link.

The summary is a compact overview, not a second list. Keep it to one sentence
with the most important two or three outcomes. The grouped bullets contain the
specific detail. Never invent a user-facing change to make a maintenance
release look fuller. Use `note` for verified internal work, and describe that
work concretely instead of claiming that no update log exists.

## Reusable authoring prompt

Copy this prompt when preparing a new release entry:

```text
为 HAPI 版本 vX.Y.Z 编写 Settings > About 的中英文更新公告。

主要依据：发行 tag 范围 `git log --no-merges <base>..<target>`、实际代码差异。
官方 GitHub Release 和 PR 仅作为辅助证据。维护者可能直接向 main 提交而没有
PR；Release 正文只有 “Full Changelog” 时，表示缺少文案，不代表没有代码变更。
不要仅凭 PR 标题或 Release 空白推断“无更新”。先按用户影响从重要到次要排序，
把同一产品区域的内容合并到一个模块标题下。每个分点只写一个明确结果，
不要写作者、PR 编号或内部实现细节。

输出并写入 web/src/lib/releaseNotes.ts：
1. 一句英文 summary 和一句等义的简体中文 summary；
2. 2～5 个清晰的模块标题（小版本可少于 2 个）；
3. 每个模块下使用 change('feature', ...) 表示新增功能，使用
   change('fix', ...) 表示修复、兼容性或可靠性改进；经 tag 差异确认只有版本、
   测试、CI、文档或内部维护改动时，使用 change('note', ...) 写清楚具体工作，
   不要编造面向用户的功能，也不要写“没有更新日志”这类占位文案；
4. 若同一版本同时有新增和修复，新增模块和分点放在修复之前；
5. 中英文保持信息一一对应，保留产品名、命令、API 名称、环境变量和代码
   格式；日期使用 UTC 的 YYYY-MM-DD；列表保持最新版本在前。

文风：面向普通用户，具体、克制、可验证。summary 只概括最重要的两三项，
详细信息放在分组分点中。不要使用“优化若干问题”“修复一些 bug”这类空话。
完成后运行 releaseNotes 单测和 Web 相关测试，检查没有重复版本、空翻译或
“查看完整发行说明”之类的占位文案。
```

## Validation

From the repository root, run the focused catalog and About tests before
building a release:

```bash
cd web
bun run ./node_modules/vitest/vitest.mjs run --config ./vitest.config.ts \
  src/routes/settings/index.test.tsx src/lib/releaseNotes.test.ts
cd ..
bun typecheck
bun run build
```
