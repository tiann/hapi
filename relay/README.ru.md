# hapi-push-relay

Официальное push-реле HAPI пересылает уведомления, защищённые сквозным шифрованием,
от самостоятельно размещённых хабов в APNs (iOS) и Firebase Cloud Messaging (Android).

## Зачем оно нужно

Официальные приложения принадлежат Apple-команде и проекту Firebase сопровождающего.
Реле централизованно хранит их **учётные данные для отправки**. Пользователи устанавливают
приложение, сопрягают текущий хаб и разрешают уведомления; им не нужны аккаунт
разработчика Apple, проект Firebase или ключ сервисного аккаунта.

Android-хабы по умолчанию используют `HAPI_ANDROID_PUSH=auto`: существующий
`FCM_SERVICE_ACCOUNT_PATH` сохраняет прямой FCM; иначе используется реле.
iOS по умолчанию `HAPI_IOS_PUSH=relay`; разработчики могут выбрать прямой `apns`.
Доставка через push-реле не зависит от сетевого туннеля хаба `--relay`.

## Модель угроз и конфиденциальность

**Реле видит только шифротекст.** Содержимое уведомления шифруется хабом
алгоритмом AES-256-GCM под ключом на устройство, который знают только хаб и
устройство. Реле, Apple и Google пересылают непрозрачные байты; iOS
Notification Service Extension расшифровывает локально на устройстве
(`mutable-content: 1` с фиксированным запасным алертом «HAPI / New
activity», который расширение перезаписывает). Android расшифровывает в своём FCM-сервисе
перед публикацией локального уведомления. Что реле *может* наблюдать — это
метаданные: платформу и токен устройства, IP подключающегося хаба/прокси, время запроса
и размер конверта. Оно не сохраняет payload в базе данных и не логирует его.
Оно удерживает состояние ограничения частоты по токену/IP в ограниченной памяти процесса, а строки
лога несут хеш токена в рамках платформы (первые 12 hex-символов SHA-256),
результат и длительность. Хеш позволяет коррелировать события одного устройства; это не полная
анонимизация. Хранение логов контейнера/прокси зависит от настроек развёртывания,
а не от политики хранения в памяти этого сервиса.

**Аутентификации клиентов нет — намеренно.** Обладание токеном устройства *и есть*
возможность отправить push, но не подделать его содержимое. Токены устройств
неугадываемы. Тот, кто получил один, может исчерпать его бюджет ограничения частоты
и вызвать общие алерты iOS, но не может зашифровать валидное содержимое без
ключа AES. Android отбрасывает нерасшифровываемые сообщения; iOS сохраняет свой общий
заполнитель. Требование аккаунтов вынудило бы самостоятельных хостеров регистрироваться в
реле — именно этого HAPI избегает. Вместо этого меры защиты:

- ограничение частоты на токен устройства: 30 push/минуту (token bucket, burst 30)
- ограничение частоты на клиентский IP: 300 push/минуту (token bucket, burst 300)
- лимит размера конверта: 3200 байт (base64 как передаётся) плюс лимит 64 КБ
  на всё тело запроса
- состояние ограничения частоты в памяти и ограничено (вытеснение LRU), без сохранения;
  у записей нет фиксированного срока истечения, они могут оставаться до вытеснения или перезапуска

## API

### `POST /v1/push`

```json
{
    "platform": "ios",
    "token": "<hex APNs device token>",
    "envelope": "<standard base64, ≤ 3200 bytes>",
    "collapseId": "optional, truncated to 64 bytes",
    "priority": 10
}
```

`priority` необязателен (`5` или `10`, по умолчанию `10`). `collapseId` необязателен
и становится `apns-collapse-id` для iOS; для Android он игнорируется.

Реле пересылает в `POST /3/device/<token>` по HTTP/2 с провайдерским JWT ES256
(кешируется, переподписывается через 45 минут), `apns-push-type:
alert`, `apns-expiration: 0` и телом:

```json
{"aps":{"mutable-content":1,"alert":{"title":"HAPI","body":"New activity"},"sound":"default"},"hapi":{"v":1,"e":"<envelope>"}}
```

Для Android используйте `platform: "android"` и непрозрачный, чувствительный к регистру FCM-токен
(непустой печатный ASCII, не более 4096 байт). Поля envelope и priority
имеют тот же формат. Реле вызывает FCM HTTP v1 для своего настроенного
проекта, используя кешированные учётные данные OAuth и следующее data-only сообщение:

```json
{"message":{"token":"<FCM token>","data":{"hapi_v":"1","hapi_e":"<envelope>"},"android":{"priority":"HIGH","restricted_package_name":"run.hapi.companion"}}}
```

Приоритет `5` отображается в `NORMAL`, `10` — в `HIGH`. Ни `notification`, ни
`collapse_key` не отправляются: Android должен выполнить локальный код расшифровки/уведомления,
а лимит FCM в четыре collapse-key не может представить произвольные id сессий.
Приложение объединяет отображаемые уведомления локально. Существующий TTL FCM по умолчанию
сохраняется. Реле не ставит отправки в очередь и не повторяет их автоматически.

Ответы:

| Статус | Тело                                  | Значение                                                                 |
| ------ | ------------------------------------- | ------------------------------------------------------------------------ |
| 200    | `{"ok":true}`                         | принято APNs/FCM (не квитанция о доставке на устройство)                                                        |
| 400    | `{"ok":false,"code":"bad_request"}`   | искажённый запрос (плюс короткое `message`)                              |
| 410    | `{"ok":false,"code":"unregistered"}`  | подтверждён недействительный токен (APNs или FCM) — хаб должен удалить этот токен  |
| 413    | `{"ok":false,"code":"too_large"}`     | конверт больше 3200 байт                                                |
| 429    | `{"ok":false,"code":"rate_limited"}`  | достигнут лимит частоты реле или провайдера — повторите позже        |
| 501    | `{"ok":false,"code":"unsupported_platform"}` | для запрошенной платформы нет настроенного провайдера |
| 502    | `{"ok":false,"code":"upstream"}`      | сбой провайдера/аутентификации/сети, включая несовпадение проекта Firebase                      |

### `GET /health`

`{"status":"ok","service":"hapi-push-relay","version":"<version>"}`

## Запуск

Из корня репозитория:

```sh
bun install
RELAY_APNS_KEY_P8_PATH=/path/AuthKey_XXXXXXXXXX.p8 \
RELAY_APNS_KEY_ID=XXXXXXXXXX \
RELAY_APNS_TEAM_ID=YYYYYYYYYY \
RELAY_APNS_BUNDLE_ID=run.hapi.app \
bun run relay/src/index.ts
```

Запуск только для Android (сервисный аккаунт должен принадлежать тому же проекту Firebase,
что и `google-services.json` официального приложения):

```sh
RELAY_FCM_SERVICE_ACCOUNT_PATH=/secrets/firebase-service-account.json \
bun run relay/src/index.ts
```

APNs и FCM независимо необязательны; настройте хотя бы один. Частичная
конфигурация APNs или нечитаемый/искажённый настроенный ключ приводит к сбою запуска.
Включите Firebase Cloud Messaging HTTP v1 API и предоставьте сервисному аккаунту реле
разрешение отправлять сообщения в этом проекте. Никогда не помещайте JSON сервисного
аккаунта в APK, репозиторий или пользовательскую конфигурацию хаба.

### Окружение

| Переменная                 | Обязательна | По умолчанию      | Примечания                                                       |
| ------------------------ | -------- | ------------ | ----------------------------------------------------------- |
| `RELAY_APNS_KEY_P8_PATH` | для iOS      | —            | путь к ключу аутентификации APNs (`.p8`, PKCS#8 PEM)               |
| `RELAY_APNS_KEY_ID`      | для iOS      | —            | key id из портала разработчика Apple                      |
| `RELAY_APNS_TEAM_ID`     | для iOS      | —            | team id разработчика Apple                                     |
| `RELAY_APNS_BUNDLE_ID`   | для iOS      | —            | bundle id iOS-приложения (`apns-topic`)                            |
| `RELAY_APNS_ENV`         | нет       | `production` | `production` или `sandbox`                                   |
| `RELAY_FCM_SERVICE_ACCOUNT_PATH` | для Android | — | JSON сервисного аккаунта с `project_id`, `client_email`, `private_key` |
| `RELAY_FCM_PACKAGE_NAME` | нет | `run.hapi.companion` | ограничить отправки FCM этим Android application ID |
| `RELAY_PORT`             | нет       | `8790`       | порт прослушивания                                                 |
| `RELAY_TRUST_PROXY`      | нет       | выкл          | `1`/`true`: ограничение частоты по первому хопу `x-forwarded-for`. Только за прокси, который перезаписывает заголовок. |

## Развёртывание

Подходит любой контейнерный хост — реле это один stateless-процесс (ограничения
частоты в памяти, поэтому запускайте один экземпляр, чего вполне достаточно: он передаёт
лишь сообщения ~4 КБ).

Используйте готовый образ `ghcr.io/tiann/hapi-push-relay`, доступный для Linux
AMD64 и ARM64. Серверу нужны только Docker и ключи/конфигурация провайдеров;
выгрузка исходников HAPI или установка Bun не требуются.

```sh
docker pull ghcr.io/tiann/hapi-push-relay:latest
docker run -d --name hapi-push-relay --restart unless-stopped \
    -p 127.0.0.1:8790:8790 \
    -v /secrets/AuthKey_XXXXXXXXXX.p8:/keys/apns.p8:ro \
    -v /secrets/firebase-service-account.json:/keys/fcm.json:ro \
    -e RELAY_FCM_SERVICE_ACCOUNT_PATH=/keys/fcm.json \
    -e RELAY_APNS_KEY_P8_PATH=/keys/apns.p8 \
    -e RELAY_APNS_KEY_ID=XXXXXXXXXX \
    -e RELAY_APNS_TEAM_ID=YYYYYYYYYY \
    -e RELAY_APNS_BUNDLE_ID=run.hapi.app \
    -e RELAY_APNS_ENV=production \
    ghcr.io/tiann/hapi-push-relay:latest
```

Смонтированные файлы `.p8` и сервисного аккаунта должны быть читаемы пользователем `bun` контейнера (UID 1000).
Используйте `production` для TestFlight/App Store и `sandbox` для приложений с подписью разработки.
Для закреплённого развёртывания замените `latest` опубликованным тегом
`sha-<full-commit-sha>` или дайджестом образа из вывода workflow.

Завершайте TLS перед ним (например, Caddy на том же хосте) — хабы отправляют
конверты через публичный интернет. Если прокси перезаписывает `X-Forwarded-For`
и является единственным входом, задайте `RELAY_TRUST_PROXY=1`, чтобы ограничение частоты по IP видело
реальные клиентские IP. Пример открывает HTTP только на loopback хоста.

Для развёртывания рядом с tunwg на том же сервере используйте
[пример Compose tunwg + Caddy + Push](https://github.com/tiann/tunwg/tree/master/examples/push-relay).
Он разделяет публичный TCP 443 и сохраняет клиентские IP для ограничения частоты.

Проверьте готовность через `curl -fsS http://127.0.0.1:8790/health`. Это проверяет
сервис, а не авторизацию у провайдера или доставку на устройство. Проверьте уведомление iOS и
Android с официальными сборками перед выпуском обновлений хаба
и приложения. Разверните сначала реле, затем хаб, затем Android. Следите в логах за
результатами `upstream`/`rate-limited` и отслеживайте использование квоты FCM в Google Cloud.
Сам FCM [бесплатен](https://firebase.google.com/pricing) с учётом
[квот проекта/устройства](https://firebase.google.com/docs/cloud-messaging/throttling-and-quotas);
хостинг и трафик реле — отдельные расходы.

### Публикация образов

Workflow [Push Relay Image](../.github/workflows/push-relay-image.yml)
запускает проверку типов и тесты реле, затем собирает обе архитектуры. Пуши в
`main`, затрагивающие `relay/`, workflow или его зависимости/входы проверки типов,
публикуют `latest` и `sha-<full-commit-sha>`. Pull request'ы собираются без
публикации. Для ручной публикации запустите **Actions → Push Relay Image → Run
workflow** на `main`; запуски на других ветках только валидируют и собирают.

Публикация использует `GITHUB_TOKEN` репозитория с `packages: write`; никаких
учётных данных реестра добавлять не нужно. После первого успешного запуска задайте
видимость пакета `hapi-push-relay` как **Public** в GitHub Packages, чтобы
серверы могли забирать его без входа. Форки публикуют под своим владельцем.

Для локальной разработки сборка из исходников по-прежнему доступна из корня
репозитория:

```sh
docker build -t hapi-push-relay:local relay/
```

## Направление хаба на реле

Обе платформы по умолчанию используют `https://push.hapi.run`; переопределите через
`HAPI_PUSH_RELAY_URL=https://push.example.com`. Существующий сохраняемый ключ
`iosPushRelayUrl` задаёт этот общий URL. Выберите `HAPI_ANDROID_PUSH=relay`
чтобы переопределить локальные учётные данные Firebase, `fcm` для прямого Android/Wear или
`off` чтобы отключить. Настроенный, но сломанный приватный аккаунт Firebase никогда
не откатывается к официальному проекту. Выберите `HAPI_IOS_PUSH=apns` для прямой
доставки iOS или `off`, чтобы отключить iOS-push.

Общий клиент хаба живёт в `hub/src/push-native/`. Доставка через Android-реле
требует обновлённого клиента телефона, регистрирующего `pushKey`; старые клиенты телефона и
Wear продолжают работать с прямым FCM. Хаб выбирает один проект/транспорт Android, поэтому сборки
с приватным проектом и сборки с официальным проектом нельзя смешивать на этом хабе.

## Замечания по реализации

- HTTP/2 к APNs использует клиент `node:http2` Bun — проверено на Bun
  1.3.14 с реальным mock-сервером `node:http2` (набор тестов проходит
  полную форму провода, включая усечение collapse-id и отображение ошибок).
  Транспорт находится за интерфейсом `ApnsClient` в `src/apns.ts`, поэтому
  его можно заменить, если обновление Bun когда-нибудь сломает поведение.
- Подпись JWT ES256 (jose) намеренно дублируется с клиентом APNs хаба:
  реле должно оставаться автономным и никогда не импортировать код хаба.
- Запускайте тесты через `bun test` из `relay/` или `bun run test:relay` из
  корня репозитория.
