# HAPI Android

Нативный Android-клиент (Kotlin + Jetpack Compose) для хаба HAPI. Полностью
независим от веб-приложения; разделяет
[контракт клиента](../docs/api/client-contract/index.md) (англ.) и сгенерированные вебом
золотые фикстуры (`shared/fixtures/`).

- **applicationId**: `run.hapi.companion` · **minSdk** 26 · **target/compileSdk** 36
- **Тулчейн**: Gradle 8.14.2 (wrapper) · AGP 8.11.1 · Kotlin 2.1.21 · Compose BOM 2025.05.00 · JDK 17+ (в CI используется 21)

## Текущие возможности

Приложение предоставляет сессии/чат, одобрения и вопросы, новые сессии,
вложения, файлы/Git, заметки, стандартную диктовку, usage/storage,
настройки и уведомления через зашифрованное реле или прямой FCM. Управление моделью и разрешениями
следует возможностям агента/сессии; usage/storage требуют пространства имён владельца. Различия
платформ, сопряжение и функции, доступные сейчас через веб, см. в [руководстве по нативным приложениям](../docs/guide/native-apps.md) (англ.).

- **Действия с сессиями:** закрепление/архивация плюс Rename, Delete и явный Reopen
  из действий списка/чата. Delete требует неактивной сессии. Resume или
  Reopen может вернуть другой id сессии: заполните её окно, перенесите черновик и
  замените навигацию возвращённым id.
- **Поле ввода:** оптимистичная отправка, очередь/steer где поддерживается, черновики и
  вложения, загружаемые при выборе. Slash-подсказки объединяют метаданные сессии
  и RPC slash-команд; у пикера навыков `$` нет UI.
- **Диктовка:** обнаружение провайдера при входе в чат выбирает первого
  провайдера с поддержкой `standard`. Микрофон скрыт, пока такой не
  доступен. Первое использование запрашивает `RECORD_AUDIO`; `MediaRecorder` записывает
  m4a/AAC, multipart-транскрипция вставляет текст в черновик, не отправляя.
  `DictationController` тестируется с фейками рекордера/API.
- **Фоновые действия:** Allow/Deny и встроенный Reply из FCM ставят в очередь
  задачи WorkManager. Воркеры находят сопряжённые хабы по сохранённым учётным данным,
  не требуя foreground `HubGraph`. Сборки без Firebase пропускают push.

## Сборка

Архитектура прокрутки нативного чата и чек-лист приёмки:
[Прокрутка нативного транскрипта](../docs/native-chat-scrolling.md) (англ.).

Требуется Android SDK для `:app`/`:core:data` (задайте `ANDROID_HOME` или
`android/local.properties` с `sdk.dir=...`). Одному `:core:protocol` нужен
только JDK.

```sh
cd android
./gradlew :core:protocol:test :core:data:testDebugUnitTest :app:testDebugUnitTest
./gradlew :app:assembleDebug :app:lintDebug
./gradlew :app:installDebug                  # connected device
./gradlew :app:connectedDebugAndroidTest     # emulator/device instrumentation
```

Без Android SDK всё равно можно запустить набор протокола, настроив
только нужные проекты:

```sh
./gradlew --no-configuration-cache --configure-on-demand :core:protocol:test
```

CI (`.github/workflows/android.yml`) запускает модульные тесты protocol/data/app,
`:app:assembleDebug`, `:app:lintDebug` и инструментацию Compose на API 29
и API 36 для PR, затрагивающих `android/**` или `shared/fixtures/**`.

### Фикстуры соответствия протокола

`:core:protocol` — цель портирования для `web/src/chat/` и проверяется
по золотым фикстурам, сгенерированным из веб-реализации.
Задача тестов уже передаёт расположение фикстур как системное свойство:

```kotlin
// core/protocol/build.gradle.kts
tasks.test {
    systemProperty("hapi.fixtures.dir", rootDir.parentFile.resolve("shared/fixtures").absolutePath)
}
```

Тесты на фикстурах читают `System.getProperty("hapi.fixtures.dir")` из
зафиксированного набора золотых фикстур. CI перезапускает этот набор всякий раз, когда меняются `android/**`
или `shared/fixtures/**`.

Фикстуры фиксируют семантику протокола/состояния, а не идентичное веб/нативное представление.
При изменении входов или генерации фикстур запустите `bun run gen:fixtures` в
корне репозитория и включите сгенерированные изменения; никогда не редактируйте фикстуры вручную. См.
[руководство по фикстурам](../shared/fixtures/README.md) (англ.).

## Сопряжение

HAPI размещается самостоятельно: приложение говорит с хабом, который запускаете **вы**. Сопряжение = передать
приложению URL хаба плюс токен доступа этого хаба; приложение проверяет хаб
(`GET /health`, требуя точного совпадения поддерживаемой версии протокола), обменивает
токен на JWT
(`POST /api/auth`), сохраняет учётные данные в `EncryptedSharedPreferences`
(с ключом на хаб — можно сопрячь несколько хабов, один активен в момент времени) и
попадает на UI сессий. Три точки входа:

1. **Сканирование QR** — хаб печатает два QR-кода при запуске с `--relay`
   (также в веб-Настройках → Companion pairing). Встроенный сканер принимает
   оба: диплинк компаньона (`hapicompanion://bind?hub=…&code=…`) и
   URL прямого веб-доступа (`…?hub=…&token=…`).
2. **Диплинк** — сканирование QR компаньона системной камерой открывает
   приложение напрямую с экраном подтверждения (intent filter `hapicompanion://bind`).
3. **Ручной ввод** — URL хаба + токен доступа, для хабов, запущенных без
   `--relay`.

### Сопряжение с хабом разработки

```sh
# Start a hub with the built-in HTTPS relay (prints the access token + QR codes).
hapi hub --relay

# Use the printed https:// URL. For a source-tree `bun run dev` hub, put an
# HTTPS reverse proxy or tunnel in front of localhost:3006 first.
adb shell am start -a android.intent.action.VIEW \
  -d "hapicompanion://bind?hub=https%3A%2F%2Fhub.example.com&code=<accessToken>"  # optional: exercises the deep link
```

Приложение отклоняет URL хабов с простым `http` при ручном вводе, в диплинках, QR-кодах
и восстановленном состоянии хаба. Манифест также задаёт
`android:usesCleartextTraffic="false"`; исключений для debug или LAN нет.
Выход из аккаунта (home → Hubs and settings → Sign out) удаляет сохранённые учётные данные
для этого хаба и убирает его из списка.

Временные сбои обновления аутентификации (сеть/5xx) сохраняют сопряжённые
учётные данные. Отклонённый токен доступа или второй 401 после успешного
обновления требуют повторного сопряжения. См. [контракт auth](../docs/api/client-contract/auth.md#silent-re-auth-401-handling) (англ.).

## Firebase / push

**Официальные сборки Firebase:** сопрягите обновлённый хаб и разрешите
уведомления. Официальная клиентская конфигурация Firebase встроена в
приложение. Хабы без приватного `FCM_SERVICE_ACCOUNT_PATH` автоматически используют официальное push-
реле; пользователи не создают проекты Firebase и не настраивают
ключи сервисного аккаунта. Нужны сервисы Google Play и связь с FCM.
Push-реле также работает с хабами, доступными через Tailscale или другие HTTPS-
настройки; оно не зависит от `hapi hub --relay`.

**Приватные сборки:** создайте проект Firebase для вашего application ID,
скачайте `google-services.json` в `android/app/` и настройте у хаба
`FCM_SERVICE_ACCOUNT_PATH` для того же проекта. Существующие настроенные хабы
сохраняют прямую доставку при стандартном `HAPI_ANDROID_PUSH=auto`. Используйте
`relay`, `fcm` или `off` для явного выбора. `HAPI_PUSH_RELAY_URL` переопределяет
общий URL реле Android/iOS. Один хаб не может смешивать сборки с приватным проектом
и сборки с официальным проектом.

**Сборки без Firebase:** плагин сервисов Google остаётся условным.
Без `app/google-services.json` Firebase не инициализируется, а пути push
становятся no-op; обычным сборкам PR учётные данные не нужны. Официальные сборки используют
отдельную обязательную проверку конфигурации (ниже).

**Зашифрованное реле:** приложение регистрирует свой FCM-токен, install ID и случайный
32-байтовый `pushKey` в каждом сопряжённом хабе. ID/ключ сохраняются вместе в
зашифрованных Keystore настройках, исключённых из облачного резервного копирования и переноса
устройства. Первое обновление заменяет старую идентичность DataStore через
дедупликацию токенов хаба; последующие ротации токена переиспользуют ID/ключ. При запуске,
сопряжении, ротации токена и повторах воркеров регистрации обновляются
автоматически. Выход из аккаунта отменяет регистрацию перед стиранием учётных данных этого хаба.

Сообщения реле несут только `hapi_v`/`hapi_e`. Расшифровка AES-256-GCM использует
тот же золотой вектор, что и iOS; содержимое уведомления недоступно реле
и Google. Неудачные расшифровки отбрасываются. Прямой приватный FCM сохраняет свой
существующий неразвёрнутый payload данных. Отрисовка, подавление при открытом чате,
воркеры Allow/Deny и Reply используют один и тот же декодированный `PushPayload` в обоих путях.
Уведомления `input-request` вместо этого показывают первый вопрос, число оставшихся
вопросов и имя сессии, используя канал `input_requests` важности HIGH. Они не предлагают Allow/Deny или Reply на сообщение: нажатие открывает сессию и
отвечает в форме вопроса.
Контракт уведомлений всё ещё не называет отправляющий хаб: воркеры действий пробуют активный хаб первым, затем другие сопряжённые хабы при промахе сессии;
нажатие открывает сессию против активного хаба.

Детали провода см. в [контракте нативного компаньона](../docs/api/native-companion-contract.md) (англ.),
настройку сопровождающего — в [развёртывании реле](../relay/README.md) (англ.).

### Официальные сборки APK/AAB

Workflow [Android Official Build](../.github/workflows/android-release.yml)
запускается вручную на `main`.
Он тестирует и загружает подписанные артефакты APK/AAB; он не публикует в Play.
Укажите новый положительный `version_code` и желаемый `version_name`.

Конфигурация репозитория, задаётся один раз сопровождающим:

| Настройка | Значение |
|---|---|
| Variable `ANDROID_FIREBASE_PROJECT_ID` | Проект, используемый сервисным аккаунтом FCM развёрнутого реле |
| Secret `ANDROID_GOOGLE_SERVICES_JSON` | **Клиентская** конфигурация Firebase для `run.hapi.companion` в этом проекте |
| Secret `HAPI_UPLOAD_KEYSTORE_BASE64` | Release-keystore в base64 |
| Secret `HAPI_UPLOAD_KEYSTORE_PASSWORD` | Пароль keystore |
| Secret `HAPI_UPLOAD_KEY_ALIAS` | Необязательно, по умолчанию `upload` |
| Secret `HAPI_UPLOAD_KEY_PASSWORD` | Необязательно, по умолчанию пароль хранилища |

`-PhapiOfficialBuild=true -PhapiFirebaseProjectId=<project>` требует
совпадающих проекта/пакета Firebase и конфигурации release-подписи.
Отсутствующие или несовпадающие настройки приводят к сбою сборки вместо выпуска пакета
без работающего push. `hapiVersionCode` и `hapiVersionName` переопределяют
обычные значения версии по умолчанию. Приватный ключ сервисного аккаунта Firebase принадлежит
только реле и никогда не должен попадать в артефакты сборки Android.

Сначала раскатайте поддержку/учётные данные реле, затем хаб, затем приложение. Проверьте
реальные фоновые уведомления, уведомления на экране блокировки и в холодном процессе на хабе
без настроек Firebase; протестируйте Allow/Deny/Reply и iOS-push перед публикацией.

## Подпись релиза

Сборки не требуют секретов подписи. `:app:bundleRelease` создаёт **неподписанный** AAB, если не настроен
upload-ключ через gradle-свойства (пользовательский глобальный
`~/.gradle/gradle.properties`), переменные окружения (секреты CI) или
`android/local.properties` (в gitignore; те же имена свойств — обычный
машинно-локальный дом, загружаемый явно, так как он не входит
в собственную цепочку свойств gradle):

| gradle-свойство | env | значение |
|---|---|---|
| `hapiUploadKeystore` | `HAPI_UPLOAD_KEYSTORE` | путь к keystore (`~` допустим) |
| `hapiUploadKeystorePassword` | `HAPI_UPLOAD_KEYSTORE_PASSWORD` | пароль хранилища |
| `hapiUploadKeyAlias` | `HAPI_UPLOAD_KEY_ALIAS` | по умолчанию `upload` |
| `hapiUploadKeyPassword` | `HAPI_UPLOAD_KEY_PASSWORD` | по умолчанию: пароль хранилища |

Это **upload-ключ** для Play App Signing (Google хранит фактический
ключ распространения, поэтому потерянный upload-ключ можно сбросить в Play Console).
Сгенерируйте его так:

```bash
keytool -genkeypair -v -keystore ~/.hapi/upload.keystore -alias upload \
  -keyalg RSA -keysize 2048 -validity 10950
```

Keystore никогда не живут в репозитории (`*.keystore` / `*.jks` в gitignore).

## Модули

| Модуль | Тип | Ответственность |
|---|---|---|
| `:core:protocol` | **чистый Kotlin/JVM** (без Android) | Проводные типы хаба, чат-конвейер, пагинация сообщений, версионированные патчи, каталоги агентов/режимов, парсеры git, ссылки сопряжения и тесты соответствия золотым фикстурам. |
| `:core:data` | Android-библиотека | Транспорт OkHttp API/SSE, аутентификация на хаб, безопасные учётные данные, хранилища StateFlow и снимки на диск, регистрация/декодирование зашифрованного push и фоновые действия уведомлений. |
| `:app` | Android-приложение | Экраны Compose для сопряжения, сессий/чата, одобрений, новых сессий, файлов, заметок, диктовки, usage/storage и настроек; навигация, локализация, сервис FCM и обвязка WorkManager. |

Направление зависимостей: `:app` → `:core:data` → `:core:protocol`.

## Интернационализация

Приложение поставляет английский (по умолчанию) и упрощённый китайский
(`app/src/main/res/values-zh-rCN/strings.xml`). Строки UI приложения
живут в ресурсах; оба файла несут **один и тот же набор ключей** (гейт — lint
`MissingTranslation`).

**Добавление строки**

1. Добавьте её в `app/src/main/res/values/strings.xml` с префиксом функции в
   ключе по существующему соглашению (`chat_`, `sessions_`, `files_`,
   `scratchlist_`, `pairing_`, `settings_`, `new_session_`, `notif_`,
   `tool_` для заголовков карточек инструментов). Динамические значения используют позиционные аргументы формата
   (`%1$s`, `%2$d`); текст, зависящий от количества, использует явные ключи `_one`/`_many`
   (намеренный стиль проекта — без `<plurals>`).
2. Добавьте китайский двойник в `values-zh-rCN/strings.xml`. **Источник истины по терминологии —
   веб-корпус** `web/src/lib/locales/zh-CN.ts` — переиспользуйте его
   продуктовые термины (会话 session, 机器 machine, 权限模式 permission mode,
   工作树 worktree, 草稿夹 scratchlist, 语音输入 dictation, 用量 usage,
   智能体/代理 agent). Технические идентификаторы (id моделей, имена flavor вроде
   Claude/Codex, метки каталога режимов разрешений, флаги CLI) остаются
   непереведёнными, как и в вебе.
3. Ссылайтесь на неё: composable-функции через `stringResource(R.string...)`. ViewModel
   остаются без строк — временные уведомления это **семантические sealed-типы**
   (`ChatNotice`, `ScratchlistNotice`, `PairingError`, `DictationErrorKind`),
   разрешаемые на слое UI; там, где ViewModel действительно составляет отображаемый
   текст, она принимает небольшой шов Strings (`FilesStrings`, `FileViewerStrings`,
   `NewSessionStrings`), чьи значения по умолчанию — английские (JVM-тесты
   конструируют без аргументов), а продакшен-экземпляр разрешается из ресурсов
   в держателях Navigation. Текст ошибок от сервера
   проходит дословно.

**Переключение языка**

`Настройки → Язык приложения` предлагает Follow system (по умолчанию) / English /
简体中文. Выбор сохраняется в `LanguagePrefs` (DataStore) и применяется
немедленно через `AppCompatDelegate.setApplicationLocales`:

- `MainActivity` расширяет `AppCompatActivity` (родитель темы
  `Theme.AppCompat.DayNight.NoActionBar`), чтобы локальные для приложения локали работали вплоть до
  API 26; на API 33+ управление берёт на себя фреймворковый `LocaleManager` (приложение также
  объявляет `android:localeConfig` для системного экрана App-languages).
- Манифест включает `autoStoreLocales` appcompat
  (meta-data `AppLocalesMetadataHolderService`), который синхронно переприменяет сохранённый
  выбор при холодном старте.
- Поверхности, разрешающие строки из **application**-контекста — уведомления FCM,
  обновления результата WorkManager, ресиверы действий уведомлений —
  оборачивают свой контекст через `localizedForAppLanguage(AppGraph.appLanguage)`
  (`di/LocaleContexts.kt`), поскольку локальные для приложения локали перенацеливают только activity-
  контексты ниже API 33.

Намеренно вне области: строки представления `:core:protocol`
(`getEventPresentation`, заголовки активности групп инструментов) остаются английскими — веб
их тоже не переводит, и паритет терминологии с вебом важнее.

## Предпросмотры инструментов

Обычные инструменты чата остаются компактными сводками. Нажатие инструмента или группы инструментов открывает нативную
страницу Navigation Compose; Back возвращает на уровень назад, Close возвращает в чат.
Группы начинаются с последнего инструмента, сохраняют позицию при возврате из
деталей и никогда не следуют за потоковыми обновлениями автоматически. Действие панели **Latest tool**
прокручивает явно. У процессов агента своя страница с
ленивыми дочерними строками. Одобрения остаются в разговоре или на живой странице процесса;
страницы деталей обычных инструментов доступны только для чтения.

Предложения планов (`ExitPlanMode` / `exit_plan_mode`) начинаются полностью развёрнутыми в
разговоре, отрисовывая полный Markdown `input.plan` до элементов управления одобрением.
Нажатие заголовка сворачивает карточку. Документы планов предварительно прогреваются в
кеше Markdown чата и не используют обычный бюджет постраничного просмотра вывода инструмента; сырой
ввод/результат остаётся под Source.
Предложения общего Codex также показывают **Implement plan** и **Continue planning**,
когда `agentState.codexPlanProposalId` активной сессии совпадает с id вызова
инструмента. Реализация использует выделенный эндпоинт плана, а не одобрение разрешения;
continue локально скрывает меню действий этого предложения и фокусирует поле ввода,
сохраняя его черновик и режим плана без отправки сообщения. Документ плана
остаётся читаемым, а новое предложение получает свежее меню. Меню остаётся видимым,
когда документ свёрнут; состояние ожидания/ошибки переживает переиспользование строк.
Отозванные, исторические и дочерние предложения остаются только для чтения (выполняющаяся
операция/ошибка всё ещё может отображаться).

Детали распознают вызовы команд/скриптов/патчей с пространствами имён, разворачивают обычные
вложенные конверты результатов и сохраняют видимыми метаданные выхода/статуса команды. Чтение
файлов использует подсветку языка исходника; текст веба/агента использует Markdown. **Source**
раскрывает исходный ввод/результат, включая поля, опущенные в предпросмотре.
Смешанные текстово-медийные результаты остаются JSON вместо отбрасывания нетекстовых блоков.

Детали вопросов показывают записанные выборы, пользовательские ответы и примечания с
Markdown-вопросами/вариантами. Вопросы выбора Codex с `isOther: true` добавляют
**None of the above** и фокусируют необязательные примечания при выборе; пустые примечания
допустимы. Переводы никогда не меняют отправляемое проводное значение `None of the above`.
Формы Pi/MCP без `isOther` сохраняют свои прежние варианты. Записанные прочие
ответы и примечания также показываются в деталях вопроса.
`request_user_input` также восстанавливает ответы из
исторических результатов; живые ответы разрешений имеют приоритет. Отвеченные карточки
избегают дублирования результатов, но сохраняют ошибки и полный ввод/результат/ответы
под **Source**. Ожидающие вопросы отвечаются в разговоре.

Вводы/выводы инструментов отображают одну часть за раз, до 20 000 графем Unicode
или 400 строк исходника. Previous/Next заменяют смонтированную часть; посещённые части
не накапливаются. Большие диффы/Markdown используют постраничный исходник. Форматирование JSON и
подготовка вывода выполняются вне потока UI. Детали мутации файла также предлагают
**View current file**, отличное от записанного ввода/результата инструмента.

Инспекторы разделяют конвейер разговора и подписку SSE. Открытие одного
замораживает следование за хвостом, отменяет скрытую загрузку истории и запись и скрывает
клавиатуру. Возврат сохраняет анкер транскрипта. Вытесненные выборки остаются
читаемыми как помеченные снимки; сброс эпохи закрывает устаревшие инспекторы.

## Длинные сообщения и раскладка чтения

Запросы пользователя остаются встроенными до 8 000 графем и 120 строк исходника. Более крупные
запросы показывают превью 2 000 графем / 24 строки, а **View full message** открывает
просмотрщик с одной смонтированной частью 4 000 графем / 80 строк. Постраничный просмотр сохраняет
пробелы, CRLF, эмодзи и комбинирующие последовательности точно; счётчики символов относятся
к графемам Unicode, а не к смещениям UTF-16.

**Copy full content** использует буфер обмена до 64 Ki единиц UTF-16. Более крупное
содержимое или сбой операции с буфером обмена предлагает экспорт в файл UTF-8 через
FileProvider и sharesheet Android; Binder получает URI, а не текст.
Экспорты старше 24 часов очищаются при следующем экспорте.

Текст тела/поля ввода/пользователя использует 16sp/24sp, код/дифф/терминал 14sp/20sp, подписи
12sp/16sp. Содержимое и поле ввода разделяют центрированную колонку чтения 720dp с
боковыми полями минимум 16dp. Ширины пузырей используют фактические ограничения контейнера,
включая разделённый экран; масштабирование шрифта Android остаётся включённым.

## Статус соединения и фильтры главной

Подзаголовок чата резервирует свою высоту. **Reconnecting · Tap to retry** появляется
после четырёх непрерывных секунд сбоя на переднем плане; переходы retry/backoff
не перезапускают этот льготный период. Состояние транспорта отделено от событий
сообщений. Изменения сети/интерфейса/маршрута по умолчанию немедленно пробуждают переподключение,
сохраняя курсоры воспроизведения; фоновые повторы откладываются до переднего плана. Локальному
маршруту хаба не нужна возможность проверки интернета Android.

Главная центрирует заголовок Sessions между иконкой **Hubs and settings** и иконкой
**Filters**, сохраняя FAB новой сессии. Меню хаба — единственный вход
для переключения/добавления хабов, настроек приложения и выхода; активный хаб отмечен.
Иконка фильтра отмечает применённый фильтр и открывает одиночный выбор Material 3
в шторке. Варианты берутся из всех сессий, включая исторические
машины; порядок определяют имена/ID, но не числа. Дубли имён включают
ID; безымянные и неизвестные машины помечены. У применённого фильтра есть действие Clear,
он временный на главную/хаб и сбрасывается, когда перестаёт быть действительным.
Держатель главной следует за экземпляром активного соединения, освобождая предыдущее
хранилище и фильтр даже при возврате к ранее использованному URL хаба.

Сопряжение и Настройки обе ссылаются на [политику конфиденциальности](https://hapi.run/docs/privacy).
Эти элементы и уведомления поставляются на английском и упрощённом китайском.

времени кадра, памяти или предиктивного назад на устройствах 60/120 Гц.
