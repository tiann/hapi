# AGENTS.md

HAPI — локально-ориентированная платформа для запуска агентов кодинга с удалённым управлением через веб/телефон.
CLI оборачивает агентов → хаб (Socket.IO) → веб/нативные клиенты (REST + SSE).

## Границы задачи

- Выполните запрошенный результат и соответствующую проверку; не останавливайтесь на первой реализации, если пользователь не просил контрольную точку ревью.
- Исправляйте причины в рамках задачи. Сообщайте о посторонних проблемах, а не превращайте их в рефакторинги или дополнительные функции.
- Принимайте разумные обратимые решения и продолжайте. Спрашивайте, когда недостающая информация существенно влияет на корректность, действие требует дополнительной авторизации или прогресс требует перезаписи чужих изменений. Продолжайте незатронутую работу.
- Сохраняйте существующие изменения пользователя/агента. Редактирование или генерация файлов не подразумевает разрешения на commit, push или релиз.
- Держите общение кратким и ясным; сообщайте результаты, выполненные проверки и оставшиеся ограничения.

## Соглашения репозитория

- Рабочие пространства Bun: `cli`, `shared`, `hub`, `web`, `website`, `docs`, `relay`. Запускайте скрипты пространства из корня; команды уровня пакета могут использовать `bun run --cwd <package> ...` или каталог этого пакета. iOS и Android используют отдельные тулчейны.
- TypeScript strict; держите код типизированным. Предпочитайте отступ 4 пробела. `@/*` разрешается в `src/*` пакета.
- Общий протокол — `@hapi/protocol`; runtime-схемы живут в `shared/src/schemas.ts` (Zod).
- Обратная совместимость для форматов, изменённых задачей, не требуется; не добавляйте слои совместимости и не меняйте посторонние форматы.

## Инварианты между компонентами

- CLI↔хаб использует Socket.IO `/cli` с токеном доступа CLI. Веб-терминалы используют `/terminal` с JWT клиента; обычные веб/нативные обновления используют REST + SSE. Сохраняйте изоляцию пространств имён (`CLI_API_TOKEN:<namespace>`).
- Обновления метаданных/состояния версионированы; сохраняйте отклонение устаревших обновлений. Управление разрешениями использует каталоги по flavor в `shared/src/modes.ts`, дополнительно ограниченные возможностями сессии.
- `shared/fixtures/**` генерируется из чат-конвейера веба — источник истины для нативного соответствия. Никогда не редактируйте фикстуры вручную. При изменениях входов или генерации фикстур (пути в [.github/workflows/fixtures.yml](.github/workflows/fixtures.yml)) запустите `bun run gen:fixtures` и включите сгенерированные изменения в результат. CI проверяет дрейф и запускает нативное соответствие при изменениях фикстур.

## Проверка и завершение

Выбирайте проверки по влиянию изменения, а не по числу шагов workflow:

| Изменение | Проверка |
|-----------|----------|
| Только документация | Проверьте отредактированное содержимое, локальные ссылки и дифф; набор тестов кода не нужен. |
| Код внутри пакета | Соответствующие тесты и typecheck пакета, где доступен; при необходимости добавьте регрессионное покрытие. |
| Общие контракты, зависимости, широкое межпакетное поведение | `bun typecheck && bun run test`, плюс затрагиваемые интеграционные/конформанс-проверки. |
| Нативный код | Соответствующие проверки из README iOS/Android доступными тулчейнами. |

- Корневые скрипты: `bun run test:<package>` для `cli`, `hub`, `web`, `shared`, `relay`; `bun run typecheck:<package>` для `cli`, `hub`, `web`, `relay`. Общие типы проверяются через потребителей. Тесты CLI/web используют Vitest; hub/shared/relay используют Bun test. Используйте фильтры файлов для целевых прогонов.
- В пределах существующих прав запускайте и повторяйте релевантные локальные проверки, не спрашивая на каждом шаге. Исправляйте сбои, вызванные задачей; сообщайте о посторонних сбоях. Если инструменты или права недоступны, выполните другую работу и укажите, что осталось непроверенным; не поднимайте нативные тулчейны и не ждите CI, если задача этого не требует.
- Переиспользуйте прошедшие проверки, когда код, зависимости и окружение не изменились; лишь переходы commit/push/PR не требуют перезапуска. Запускайте общепроектные проверки также при явном запросе.
- Просмотрите изменения этой задачи на корректность, безопасность и регрессии. Для локальной работы изучите незастейдженные/застейдженные диффы (`git diff`, `git diff --cached`) и новые файлы; для ревью ветки/PR используйте дифф от merge-base фактической целевой ветки. Локальное саморевью не требует события GitHub, удалённого ревью или публикации комментариев.
